# Remote browser (`/go`) implementation plan

Implement a remote browser, served at `<base>/go`: [Moli](https://github.com/lexmount/moli), a headless browser engine, loads and runs each page on the TabTop host inside a sandbox, and the client displays a sanitized rendering of the resulting DOM. All destination traffic leaves from the TabTop host, and everything between the client and TabTop travels through TabTop’s authenticated E2E tunnel.

Moli was chosen after two rounds of hands-on comparison: Lightpanda against Kitesurf, then Lightpanda against Moli and Obscura (section 0). Moli supplies page loading, script execution, and the DOM. The session handling, sandbox, egress control, transport, and client renderer remain TabTop’s work.

## 0. Goals, decision, and evaluation results

### Goals

- Read and interact with web pages from a client that should not contact the destination directly: all destination traffic leaves from the TabTop host, through the E2E tunnel.
- Keep website code away from TabTop’s session, tunnel, files, and host, even when the website is hostile.
- Make unsupported features visible rather than silently broken.

### Target page classes

Compatibility is measured against these:

1. Static and documentation sites (HTML/CSS, images, fonts, anchors).
2. Pages with progressive enhancement: menus, tabs, disclosure widgets, client-side search.
3. GET/POST forms (search boxes, basic submissions).
4. Interactive pages and internal tools whose scripts use common DOM APIs, `fetch`, and WebSocket.
5. Moderate single-page applications, as far as Moli supports them.

### Non-goals

- Current unsupported content: WebRTC and video and audio a site’s own player streams (Media Source), as YouTube’s does. WebGL uses the bounded replay subset in section 6. Canvas2D is copied as bounded PNG snapshots after drawing calls; see section 6. Video and audio with a file to play are played (section 6).
- Logins and persistent destination sessions until Phase 3 decides cookie handling (see section 4).
- Service workers and browser extensions. Embedded pages (iframes) are sanitized copies with supported input routed to the engine (section 6), not browser frames in the viewer.
- Filesystem access for pages.

### Decision

**Moli, driven over CDP, with a DOM snapshot rendered by the client.** Recorded 17 November 2026 after the second comparison round below. It replaces Lightpanda, chosen earlier the same day after the first round.

Reasons, from the measurements:

- **Containment equal to Lightpanda’s** in the same sandbox and egress proxy: every private, metadata, and loopback probe refused at the proxy, including WebSocket; no direct connection reached a loopback service; sandbox escape probes blocked.
- **CDP DOM mutation events** (`DOM.childNodeInserted`, `DOM.childNodeRemoved`). Changes are reported by the engine itself, not by an observer injected into the page’s process; an isolated-world observer also works as a fallback.
- **A built-in script watchdog** that ended a looping page after about 8 s while other CDP sessions kept working (Lightpanda’s took about 30 s).
- **MIT or Apache-2.0** at the user’s option, compatible with TabTop’s Apache-2.0; Lightpanda is AGPL-3.0.
- **Coordinate input fails loudly**: without layout, `Input.dispatchMouseEvent` is refused with an explicit error instead of hitting an element chosen from approximate boxes.
- No telemetry observed: every host in the proxy log during Moli’s runs was one the pages themselves contacted.

Accepted costs:

- About twice Lightpanda’s memory after the same pages (109 MB against 57 MB; peak 160 MB against 85 MB), and slower on some pages (Wikipedia about 1 s against 0.1 s).
- A 112 MB binary that also needs fontconfig, freetype, libpng, brotli, bzip2, expat, zlib, and libstdc++ from the system.
- CDP over TCP only. In sandboxed mode a bridge connects it to a Unix socket outside the sandbox’s network namespace. In unsandboxed override mode it listens on host loopback without authentication (section 3).
- A young, fast-moving, vendor-driven project (Lexmount also sells a hosted product); pin releases.
- A default Docker container cannot run the sandbox (section 3, “Sandbox modes”).

### Other observations

- **Proxy routing is complete for Lightpanda and Moli.** For Lightpanda, every request path — document, scripts, images, stylesheets, iframes, `fetch`, XHR, EventSource, `sendBeacon`, and WebSocket (as `CONNECT`) — went through the HTTP proxy for `127.0.0.1`, `localhost`, `[::1]`, `127.1`, `0.0.0.0`, and `[::ffff:127.0.0.1]` alike. For Moli, the same paths plus top-level navigation were checked in Phase 1 against tabtopd’s own proxy (`TestGoProxyWithMoli`): all refused, and the target service saw no request. (A first-round reading that Lightpanda bypassed its proxy for localhost was wrong: those probes used port 9, a Fetch “bad port” refused inside the engine.)
- **The proxy must check `CONNECT` targets.** A test proxy without that check let a page’s WebSocket reach a loopback service.
- **Moli does not fetch images, fonts, or media unless asked** (`--image`, `--font`, `-r`); scripts and stylesheets are fetched. Images and fonts for display come from the client’s resource broker (section 4).
- **Moli sends page beacons** (`sendBeacon`, analytics endpoints) that Lightpanda skips by default; they go through the proxy like any other request.
- **Moli honours `NO_PROXY` / `no_proxy` and `--http-no-proxy`**, which would bypass the proxy; the engine’s environment must not contain them.
- **HTTPS goes through `CONNECT` tunnels**, so the egress proxy sees host and port, not the full URL; destination policy still applies at dial time.
- **Memory stays allocated across sessions in one engine process**, which supports one disposable engine per browsing context.
- **Kitesurf runs page scripts natively in V8** inside `workerd` isolates, so it needed the same host sandbox; `workerd`’s README states it “is not a hardened sandbox”.
- **chromedp v0.23 changed to a generic API**; earlier spikes used v0.14.2. Phase 1 used neither: tabtopd has a small CDP client of its own (`gocdp.go`) over `github.com/coder/websocket`. That library closes a connection whose write's context ends, and the CDP connection is the tab's for every call, so a call is written apart from its caller's context (bounded by a timeout of its own) and only the wait for its reply is given up: a load replaced by another, as its `Page.navigate` is sent, doesn't take the tab's engine with it.

Not yet covered, carried into Phase 1:

- Running Moli in the sandbox without `/proc` — done at the start of Phase 1: it works (see section 3).
- A seccomp filter and a minimal filesystem view (the comparison bound all of `/usr` and `/etc/fonts` read-only).
- Form submission, navigation after following a link, attribute and text mutation events, and reliability over long interactive sessions.
- arm64: out of scope for the first release (CI builds and ships amd64 images only). The arm64 Moli is pinned and the arm64 seccomp filter type-checks, but neither has run on arm64; test both before shipping an arm64 image.

### Evaluated and not chosen

Recorded so they are not re-proposed without new information:

- **Lightpanda** (tested, both rounds): lighter and faster on some pages, CDP on a Unix socket, but AGPL-3.0, telemetry on by default, no CDP DOM mutation events, and a slower script watchdog. The fallback if Moli fails in Phase 1.
- **Obscura** (tested, round 2): WebSocket is fake (reports `open` without connecting), its isolated world is not isolated, and it emits no DOM mutation events, so it offers no tamper-proof way to stream page changes. Its built-in private-network block also blocks a proxy-reached loopback page unless `--allow-private-network` is set.
- **Kitesurf** (tested, round 1): slower, heavier, canvas-only, freezes entirely on a looping page, and depends on an experimental `workerd` feature. Revisit if open-source `workerd` enforces per-isolate CPU limits.
- **OxiBrowser** (reviewed, not tested): JavaScript in the Boa interpreter (expected to be much slower, as with Kitesurf), essentially one maintainer, inconsistent documentation, very fast release cadence.
- **Servo** (reviewed, not tested): a full rendering engine with SpiderMonkey and WebDriver Classic but no CDP; using it means writing a Rust embedding program, and its layout and painting would be wasted on a DOM-snapshot design. Reconsider only if `/go` switches to streaming pixels.
- **Static sanitized browser (no page JavaScript)**: most target classes need scripts.
- **Headless Chromium on the host**: heavy per-session host cost and a large dependency. The default image (`DESKTOP=xfce`) already offers Chromium on the streamed desktop for pages that need full compatibility.
- **QuickJS virtual browser** (page scripts in QuickJS/WASM on the client against a hand-written DOM): writing and maintaining the DOM and browser APIs is the dominant cost, and compatibility would remain narrow.

### Industry reference: Cloudflare Browser Isolation

[Cloudflare Browser Isolation](https://www.cloudflare.com/sase/products/browser-isolation/) gives each user a disposable, containerized headless Chromium, treated as compromised and destroyed after each session, and (per the [2020 S2 Systems acquisition post](https://blog.cloudflare.com/cloudflare-and-remote-browser-isolation/)) streams Chromium’s draw commands to a WebAssembly renderer in the user’s browser. Per-session disposal and controlled egress are the same baseline hardening this plan adopts in section 3. TabTop needs no TLS interception: the user enters the URL in `/go`, so the engine fetches it directly.

## 1. Architecture

```text
client: <base>/go — trusted UI
  ├─ Address bar, history, reload, stop, errors
  └─ Sandboxed rendering iframe
       ├─ Trusted rendering agent
       ├─ Sanitized DOM, with brokered images, stylesheets and fonts
       └─ Events by node ID → host; snapshot and mutations ← host
          ⇅ existing E2E tunnel
host: tabtopd
  ├─ Browser session manager (one Moli process per browsing context)
  ├─ CDP client ── Unix socket ── bridge ── Moli on 127.0.0.1 inside its sandbox
  │                                          (DOM mutation events; isolated-world observer as fallback)
  ├─ Egress proxy dialling through fetch.go’s address policy ← bridge ← all engine traffic
  └─ Resource broker for the renderer (images, stylesheets, fonts)
```

Keep session secrets, tunnel objects, and filesystem capabilities in the trusted UI. The rendering frame receives only serialized content and narrowly scoped messages.

E2E protects the client-to-TabTop connection. The engine or broker fetches the destination through HTTP or HTTPS; the destination and gateway see the requested content, and the destination sees the TabTop host’s IP address.

### Security layers and which one is load-bearing

- **Host containment (load-bearing):** the engine’s process sandbox, network namespace, and resource limits (section 3). A fully compromised engine must be unable to read TabTop’s files or state, reach tabtopd except through its CDP socket, or connect anywhere except the egress proxy. In the unsandboxed override mode (section 3) only the egress proxy remains, so it must check every request, `CONNECT` included.
- **Client containment (load-bearing):** the rendering iframe’s sandbox and CSP. Even with a completely broken sanitizer, snapshot content must be unable to reach the parent DOM, TabTop storage, the tunnel, or the network.
- **Frame navigation (load-bearing):** the frame's CSP doesn't limit navigation; the `/go` page's `frame-src 'self'` does. A link or script that sends the frame to another site is blocked (tested: no request leaves), the frame shows the browser's error page, and `go.js` puts its own document back. Messages from the frame carry a per-document token, so no other document in it is heard. Links in snapshots never keep their address (`href="#"`, the address kept by the agent), and `href` is denied by default on every other element.
- **Broker enforcement (load-bearing for "no direct traffic"):** the frame CSP permits no network origins at all — only `'self'` for the trusted renderer, `blob:`, and `data:`. A URL the rewriter misses fails to load rather than leaking a request.
- **Sanitizer and rewriter (correctness and defence in depth):** removes active content from snapshots and rewrites resource URLs to broker-backed `blob:` URLs. A sanitizer bug should cause broken rendering, not an escape or a leak; tests confirm this by disabling the sanitizer and checking that the layers above still hold.

## 2. Reuse existing TabTop components

Build on:

- `tabtopd/tunnel_routes.go`: authenticated request dispatch.
- `tabtopd/tunnel_request.go`: request envelopes and streamed responses.
- `tabtopd/fetch.go`: `newFetchClient` and `fetchPolicy`/`fetchAllowed`, which already check the address on the socket actually opened (covering DNS rebinding, redirects, and odd spellings of local hosts), block this machine’s addresses, link-local and cloud metadata ranges, and use no proxy. The egress proxy and the resource broker must both dial through this policy, not a new one.
- `tabtopd/preview_resource.go`: per-request limits, slot limiting (`previewResourceSlots`), redirect handling, and the `WEB_GO_FETCH=0` off switch.
- `tabtopd/preview-html-resources.js` and `tabtopd/preview-css.js`: resource resolution and CSS rewriting for the renderer.
- `tabtopd/page_assets.go`: embedded assets and frame/worker CSP patterns.

Add dedicated browser routes rather than broadening `preview-resource`, whose accepted types and limits serve a different purpose.

**Do not reuse the existing preview frame settings.** `frameSandbox` (`page_assets.go`) and `sandboxFrame` (`preview-frames.js`) grant `allow-popups allow-popups-to-escape-sandbox`, and `directFrameCSP` allows `http:` and `https:` loads. Both would let page content bypass the broker. `/go` gets its own sandbox string (`allow-scripts` only), its own CSP constant, and its own frame helper, with a test asserting their exact values.

## 3. Engine service and host sandbox

### Moli as a component

- Pin a release (1.1.25 at the time of the comparison) and verify its published SHA-256 on install. Release archives exist for Linux x86_64 and aarch64 (glibc), macOS, and Windows.
- MIT or Apache-2.0, so it may be bundled in the image; keep its license files and `license-metadata.json` (Chromium BSD and Selenium notices included) with it. Install the system libraries it links against (fontconfig, freetype, libpng, brotli, bzip2, expat, zlib, libstdc++). `/go` reports itself unavailable when the binary is absent.
- Run as `moli serve --host 127.0.0.1 --port <port> --http-proxy http://<user>:<password>@127.0.0.1:<proxy-port> --user-agent <fixed> --layout` with no `--image`, `--font`, `--resource`, `--cookie-jar`, or `--profile-dir`, and with no `NO_PROXY`/`no_proxy` in its environment. `--block-private-networks` is not used: it applies only to directly connected targets, and all targets go through the proxy.
- `--layout` (added after Phase 2) gives pages real sizes and places, so a page that measures itself (a menu placed under its header) works. The engine’s window is the person’s frame: its size and pixel ratio come with each navigation and with each resize (`{"op":"viewport",…}`), set with `Emulation.setDeviceMetricsOverride`; `screen` is the person’s window (the `/go` page’s, which the frame is within), so a page sizing itself to the display does so to what they see, and their own screen isn’t told. Which way up the device is held goes too (`screen.orientation`'s type and angle, or, where the device doesn't say, the window's shape), as `setDeviceMetricsOverride`'s `screenOrientation`, again when it turns (a half turn changes no size): the page's `screen.orientation`, its `(orientation: …)` media queries and their `change` events, and `resize`, follow it (Moli; an engine that refuses it is sized all the same). Moli has no `window.orientation` nor `orientationchange`, as desktop Chrome hasn't. A device with touch (`navigator.maxTouchPoints`) has the page told so too (`Emulation.setTouchEmulationEnabled`: `ontouchstart`, `maxTouchPoints`), as a page offers touch screens what it offers them. Light or dark as the person’s browser (`matchMedia("(prefers-color-scheme: dark)")`, and again when it changes) goes as `view.scheme`, set with `Emulation.setEmulatedMedia` (`prefers-color-scheme` light or dark): the page’s `(prefers-color-scheme: …)` rules and `matchMedia` / `change` in the engine follow it (an engine that refuses is left as it was). Moli computes layout once a page loads and again at the next CDP evaluation after a script changes the page (every act and change poll is one); a resize alone doesn’t, so a one-pixel `Page.captureScreenshot` follows it (3 ms). Geometry is close, not exact: the engine has its own fonts (DejaVu in the image) and loads no web fonts or pictures. Moli’s `IntersectionObserver` never reports anything visible, with or without layout, so `/go` answers it from the person’s browser instead (below). Measured with it: the same elements and pictures on the real sites as without; 60 pages in one tab, the engine at most 259 MiB and tabtopd 150 MiB, about 15% slower in all. Sites learn the window’s size and pixel ratio, where before every tab looked 1920×1080.
- No telemetry was observed; Phase 1 confirms this from the egress proxy log over longer sessions.

### Engines: Moli or Obscura

- The engine is chosen by `-go-engine` (`WEB_GO_ENGINE`: `moli`, `obscura`, or a binary's path), recognised by its file's name or `--version` (`goAdapterFor`). An adapter (`goAdapter`, `goengine.go`) is what differs: its arguments (proxy, user agent, the shared cache's directory), whether it takes the shared HTTP cache (Moli does; Obscura has none), its data segment's limit (Obscura's V8 reserves address space that `RLIMIT_DATA` counts: 1.25 GiB to start, so 8 GiB; resident memory is held to the same 1 GiB by the watchdog for both), and whether its page's events come on a session of its own too (Obscura: some on both, and those caused by input on its own only, so they're taken from any session, a copy of one of the last 32 passed over). The sandbox, proxy, bridge, agent, frame and tests are the same for both. The image bundles Moli; Obscura must be supplied separately. Moli is the default.
- What the agent does was made right for both, without asking which: a same-origin frame's markup is compared, once a second at most, as well as watched (Obscura's observers miss what changes in another window's document; the frame's own `MutationObserver` can't be used: in both engines a frame's window, seen from the agent's world, is the page's own, which a page can replace to be handed the agent's callback and, through its constructor, run code in the agent's world, forging what it reports, the address included; checked end to end); the address is `location.href` (Obscura's `document.URL` misses a fragment followed); a field's value is set through the nearest setter along its prototypes, or assigned (Obscura's `HTMLSelectElement.prototype` has none). The proxy's refusals carry `X-Tabtop-Go-Refused` (a reason, from a fixed list; taken out of sites' responses): Obscura shows a refusal as the page where Moli fails the load, and either way the person is told why.
- What Obscura leaves out of input is done by the agent (`__tabtop.scripted`, for an adapter with `scriptedInput`), measured against Moli on the same page: pointer events (`pointerover`/`enter`/`move`/`down`/`up`, `pointerout`/`leave`), `mouseenter`/`mouseleave` along the ancestors entered and left (Obscura gives `mouseenter` to the element under the pointer alone, and no `mouseleave`), the right click's `contextmenu`, Tab moving the focus, and Space (on release) or Enter pressing what has the focus, as a click given there as input (trusted, as a browser's). It takes a release outside its window as one on what was pressed, a click: a press let go outside is ended by another button's release, which makes none.
- Its `alert`, `confirm` and `prompt` it answers itself, at once, and says nothing of; synchronous `XMLHttpRequest` fails at once too (status 0), so the page can't be made to wait for the person. `godialogs.js` (in the page's world, for an adapter with `noDialogs`) tells the agent what was asked, which sends it with the changes; the person is shown it (`go-dialog-notice`), one after another, with a note that a question got the engine's answer, and may stop a page's (as for real dialogs).
- Obscura 0.2.7 passes 35 of the 40 end-to-end checks (Moli, all; November 2026). Not there: a prompt answered (above), windows the page opens (no target), a page laid out again at a new window size, native drag and drop, and a video the page gives a file and plays (`video.src` set by script isn't reflected to its attribute, and no media events). Neither it nor Moli, Lightpanda or headless Chrome gets through Cloudflare's managed challenge (forcoder.net, measured; Obscura's stealth build too).

### Lightpanda

- `goAdapters["lightpanda"]` (Lightpanda 1.0.4, AGPL-3.0; recognised by its file's name: its `version` says only the number): run with `--http-proxy`, `--disable-metrics`, the shared HTTP cache (`--http-cache-dir`), stylesheets, iframes and workers loaded (`--load-resources`; it loads none by default, so a page's frames wouldn't be there), and `LIGHTPANDA_DISABLE_TELEMETRY=true` (it reports usage by default; sandboxed it couldn't reach out anyway). It refuses a User-Agent with "Mozilla" in it, as every browser's has, so it says it's Lightpanda. It starts within a 512 MiB data limit: the default (1 GiB) stands. An adapter's `env` is set in its sandbox (`--setenv`) or unsandboxed environment.
- Its places aren't a browser's (no layout to speak of: a move to one element lands on another, a click on `<html>`), so the mouse is given by script to the element the person pointed at (`goInputGaps.byElement`, the agent's `mouse`: pointer and mouse events, entering and leaving along the ancestors, press, release and click, double and right clicks, the wheel, scrolling what can be). Those events aren't trusted (`isTrusted` false), and Lightpanda doesn't work out `offsetX` for them (0). Its keys are a browser's but for Enter pressing a button, which the agent does.
- Its MutationObserver records, for changes the page's own script made, name the page's world's nodes, not the agent's: the agent can't number them, and mustn't touch them (their prototypes are the page's). It checks (`instanceof Node`, which runs no page code) and asks for the document to be read again whole (`again`, `readAgain`), at most each `goAgainEvery`; a read again keeps the focus, its caret and what's typed that hasn't been sent (`keptFocus` in `go-frame.js`). For Moli and Obscura nothing changes: their records are the agent's world's.
- A window the page opens is another top-level frame of the same target, not a target: its address is loaded in the tab, as a popup's is. A load it fails (`ERR_UNSAFE_PORT`, say) it then shows a page of its own for: nothing of a generation whose load failed is shown. A dialog still open when the page goes (it opened a window, then asked) is sent again with the next generation (`askAgain`).
- 33 of the 40 end-to-end checks pass. Not there: the trusted and positioned clicks above, a page laid out again at a new window size, `prompt` answered by the person (a dialog, but its default isn't given), native drag and drop, and a video the page starts. The image doesn't have it: its licence (AGPL-3.0) asks for its source to be offered with it.

### Lifecycle

- One Moli process per browsing context, started on `browser-open`, killed on `browser-close`, logout, session expiry, tunnel loss, or idle timeout. No engine state outlives its context. Start-up measured at 35–77 ms, so there is no need to pool engines.
- Moli’s own watchdog ends a looping script after about 8 s. tabtopd’s watchdog is the outer limit: it pings the engine over CDP and watches its CPU and memory, and kills an engine that stays over budget or stops answering.

### Sandbox modes

At start-up tabtopd probes whether bubblewrap can create its namespaces, and `/go` runs in one of three states:

1. **Sandboxed** (probe passes): the engine runs in bubblewrap as below.
2. **Unavailable** (probe fails, no override): `/go` reports that it is unavailable and why, and how to enable it.
3. **Unsandboxed** (probe fails and `WEB_GO_UNSANDBOXED=1` / `-go-unsandboxed` is set): the engine runs as a plain child process of tabtopd. tabtopd logs this at start-up and for each tab opened. Never chosen silently.

The override exists because most full TabTop containers are disposable. Its risks:

- A page that exploits a Moli or V8 bug runs native code with tabtopd’s user, files, and network access.
- Moli’s CDP listens on host loopback with no authentication (it checks only the `Origin` header), so any local process can drive the engine while it runs. tabtopd uses a random port per context; this is acceptable only for disposable containers.

Without an engine exploit, page traffic is still confined by the egress proxy: in the comparison, Moli sent every request path through `--http-proxy`, and a loopback service saw no direct connection.

Findings in Docker (Docker’s built-in seccomp profile and `docker-default` AppArmor, Debian trixie image):

- With default settings, bubblewrap cannot create any namespace, as root or as an unprivileged user.
- `--security-opt seccomp=unconfined` alone or `apparmor=unconfined` alone is not enough; both together are.
- Mounting a fresh `/proc` additionally needs `--security-opt systempaths=unconfined`. Moli runs without `/proc`, so the sandbox omits `--proc` and needs only the first two. Tested at the start of Phase 1 in a `debian:trixie-slim` container as an unprivileged user: Moli 1.1.25 loaded example.com and Wikipedia in the sandbox, without `/proc`, through the egress proxy.
- These options relax the whole TabTop container, not just the engine. A seccomp profile derived from Docker 26.1.5’s default — dropping its `CAP_SYS_ADMIN`-only restrictions on `clone`, `clone3`, `unshare`, `setns`, `mount`, and `umount2`, and allowing those and `pivot_root` — works in place of `seccomp=unconfined`. Docker’s `docker-default` AppArmor profile still blocks namespace creation with it, so `apparmor=unconfined` (or a host-loaded AppArmor profile) remains necessary. Phase 1 ships the seccomp profile and documents both routes.
- On hosts (lite installs) bubblewrap works without extra settings.

### Sandbox

The comparison used bubblewrap, which worked without root on the test host:

- `--unshare-all` (new user, PID, IPC, UTS, cgroup, and network namespaces), `--cap-drop ALL`, `--die-with-parent`, `--new-session`, `--clearenv`.
- A read-only view of the engine’s binary alone (not its directory, which could be someone’s home), the system’s libraries, fontconfig’s configuration, and CA certificates; a private `/tmp` capped at 256 MiB; the run directory read-only, holding only the CDP and egress sockets. tabtopd creates the CDP socket and hands it to the bridge as file descriptor 3, so the bridge needs no write access there. No access to `$HOME`, roots, tabtopd’s state or other sockets, or the X display.
- No `--proc`: Moli runs without it (tested on the host and in Docker).
- A seccomp filter (`goseccomp.go`), passed to bwrap as `--seccomp`: a denylist like Flatpak’s, built by tabtopd as classic BPF for the architecture it’s built for (x86-64 and arm64). It refuses keyrings, BPF, `userfaultfd`, `io_uring`, `perf_event_open`, `ptrace` and `process_vm_*`, new namespaces and mounts (including `clone` with a namespace flag; `clone3` gets `ENOSYS` so glibc falls back to `clone`), modules, kexec, clocks, and the TIOCSTI and TIOCLINUX ioctls; sockets are limited to Unix, IPv4, IPv6 and routing netlink; another architecture’s calls (x32) kill the process. The startup probe runs with the filter too. Tested: `unshare -U` and AF_ALG, AF_VSOCK and netfilter sockets work without the filter and are refused with it; Moli runs under it on the host and in the image.
- `/usr` stays bound whole, read-only: it’s the distribution’s public files, and narrowing it to the binary’s libraries would break with each Moli or Debian update for little gain.
- Confirmed in TabTop’s image (`GO_IMAGE=… test/go-check.sh`, also in CI): `tabtop-lite` with the seccomp profile and `apparmor=unconfined` runs `/go` sandboxed, every end-to-end check passing.

### Bridges

The engine’s network namespace contains only loopback. A small bridge inside the sandbox — tabtopd itself, run with a bridge subcommand and bound in read-only — forwards both ways:

- **CDP in:** a Unix socket in the run directory to Moli’s CDP port on `127.0.0.1`. tabtopd connects to the socket and sends the `Host` header Moli expects.
- **Egress out:** `127.0.0.1:<proxy-port>` (Moli’s `--http-proxy`) to the egress proxy’s Unix socket.

In unsandboxed mode there is no bridge: the proxy listens on loopback TCP with per-context credentials, and tabtopd connects to Moli’s CDP port directly.

### Shared HTTP cache

The engines share Moli’s HTTP cache (`--http-cache-dir`, `gocache.go`): one directory on disk (`~/.cache/tabtop/go-http-cache`, private to TabTop’s user), bound writable into each engine’s sandbox at `/cache` (or given as it is, unsandboxed), so a site’s scripts and stylesheets fetched in one tab are on disk for the next and survive restarts. Measured: GitHub in a fresh engine took 23 of its 105 requests from it, its document ready 0.5 s sooner; `TestGoCacheWithMoli` has a second engine load a page without asking for its script or stylesheet again. Moli doesn’t bound it; tabtopd prunes it to 512 MiB, the entries used longest ago first, at start-up and as tabs close (at most once a minute). `WEB_GO_CACHE=0` (`-go-cache=false`) turns it off.

**Site controls → Browser-wide → Clear cached files** (tunnel request `go-cache-clear`, `gocache.go`) empties it (every entry; the directory stays, for the engines using it), has each open tab's engine clear its own (`Network.clearBrowserCache`), and forgets what each tab fetched for its copy, on the server (`goResCache`) and in the person's browser (go.js's, with a same-origin broadcast to open tabs). Sites' cookies and storage are kept: go/cookie clears those. Checked end to end: a picture shown twice is fetched from its site once; after Clear cache, again.

Chosen with its costs, which a per-tab engine didn’t have: the engines write it themselves, so one taken over by a page could change what’s cached for another site, which later tabs then run (its compromise outliving its tab), or fill the disk through it between prunings; and Moli keys entries by address alone, not partitioned by the site that asked as browsers now are, so a site can time another site’s resources to learn whether they were fetched before. A cache tabtopd itself fills, read-only to the engines, was considered and set aside for now (it relies on Moli’s cache format and re-fetches without cookies).

### Resource limits

Memory is capped by `RLIMIT_DATA`, which V8 tolerates where it doesn’t tolerate `RLIMIT_AS`. The bridge sets it on itself just before starting the engine, which inherits it; unsandboxed, tabtopd still starts the engine through the bridge, forwarding nothing, for this. Measured in Phase 1: Moli needs at least 640 MiB to start (512 MiB crashes it); with the default 1 GiB, a page allocating as fast as it can was stopped at a 473–479 MB peak, on the host and in Docker, sandboxed and not. A 1-second watchdog alone let the same page reach 1.2–1.46 GB first. The watchdog’s resident-memory check remains a second layer.

The sandbox’s `/tmp` is a tmpfs capped at 256 MiB (`--size`). Moli keeps cookies and IndexedDB in `TMPDIR` (`moli-storage-*`) when it has no profile; unsandboxed, `TMPDIR` is inside the run directory, removed when the engine is killed (Moli deletes it only on a clean exit).

The comparison used a systemd user scope (`systemd-run --user --scope -p MemoryMax=… -p MemorySwapMax=0 -p CPUQuota=100% -p TasksMax=…`), which killed a memory-exhaustion page at the limit without affecting anything else. Containers usually have no systemd, so the portable floor is tabtopd’s own watchdog: it polls each engine’s resident memory and CPU time and kills it over budget, and caps the number of live engines (3 per login, 8 in all). CPU counts only while nobody is using the tab: each message from the person restarts the 60-second window, since loading a heavy site legitimately takes more than a core for seconds (GitHub: 3.5 s of CPU in 3.3 s). The first long-session run, 60 real pages back to back, was killed as busy at page 23–29 before this; Moli itself idles at under 1% of a core after 25 heavy pages, so nothing was left running. Measured after the fix: 60 pages in one tab (Wikipedia, Hacker News, GitHub, MDN, DuckDuckGo), all shown, the engine at most 218 MiB resident, tabtopd 136 MiB. A cgroup limit is added where one can be created. Do not use `RLIMIT_AS`, which breaks V8’s address-space reservations.

### Egress proxy

The proxy handles plain proxied requests and `CONNECT`, and dials every connection through `fetch.go`’s address policy, checked on the socket actually opened:

- HTTP/HTTPS only; public destinations by default; private networks only when separately configured (a browser-specific flag alongside `-fetch-private`/`previewFetchPrivate`, defaulting off); loopback, link-local, metadata, and the host’s own addresses never.
- Ports 80 and 443 only, for `CONNECT` and plain requests alike (`goProxyPorts`), with the same address check for both. HTTPS and WebSocket pass through `CONNECT` tunnels, so rules are per host and port; URL-level rules apply only to plain HTTP.
- Plain requests are forwarded with the transport’s `RoundTrip`, so the engine sees and follows redirects itself, each one checked again.
- `WEB_GO_FETCH=0` disables `/go`.
- Per-context limits on connections, bytes, and request rate, since all traffic originates from the TabTop host’s IP. Done: 64 connections at once, requests and tunnels at 30 a second after a burst of 300, and 4 GiB in all, both ways, for the engine’s life (`goProxyBudget`); then requests get 429 and open tunnels close.
- Logging matching `fetch.go`: the destination host only, never the full URL.

### DNS over HTTPS

Off by default: names are looked up by the system's DNS, as before. In ☰ → Settings → DNS over HTTPS it can be Cloudflare's, Quad9's, or a custom DoH server (an https address; `/dns-query` if it has no path), kept with the browser-wide settings (`go-sites.json`: `doh`, `dohURL`) and in force at once for every tab (`godoh.go`, `goDoHNow`). A server's taken only once it has answered a lookup.

- Where it applies: the engine's tunnels (the egress proxy's dialer), and the server's fetches for the browser: its pages' resources and media, its downloads, its filter lists (`newGoFetchClient`, `goDialer`). Not the Files page's fetches nor previews': they keep the system's DNS.
- While it's on, it's the only DNS: a name it doesn't find, or can't say of (SERVFAIL, no answer in time), isn't reached, and the system's DNS isn't asked instead. A local or private name doesn't resolve either, unless it's in the local records or `/etc/hosts` (below): use its address, or give it one there; `WEB_GO_PRIVATE` doesn't change that (it lets the browser reach private addresses, not look up private names). The proxy refuses such a tunnel with `dns`.
- Its answers go by the address policy as any other address does (dropped, before they're dialled, where the browser mayn't go), and are kept for their TTL (from 30 seconds to 5 minutes; a name not found, 30 seconds).
- RFC 8484, POST of `application/dns-message`, A and AAAA asked together. The DoH server's own name never goes through it: a preset's addresses are pinned (1.1.1.1, 1.0.0.1 and Cloudflare's IPv6; 9.9.9.9, 149.112.112.112 and Quad9's IPv6); a custom server's name is looked up once by the system's DNS, and again only if it can't be reached there. A DoH server on a private network or this machine is refused.
- Nothing logs the names looked up.

### Local DNS records

In ☰ → Settings → Local DNS records, names can be given addresses (A and AAAA records: a name and an IPv4 or IPv6 address, as many rows per name as it has addresses), kept with the browser-wide settings (`go-sites.json`: `hosts`, at most 256) and in force at once for every tab (`gohosts.go`, `goHostsNow`). A name is looked up, wherever DoH applies (`goDialer`), in this order: these records; then this machine's `/etc/hosts` (`goetchosts.go`: a container's `--add-host` lines among them; read again as it changes, looked at every 5 seconds at most); then DNS over HTTPS while it's on, else the system's DNS. A custom DoH server's own name is looked up in these records first too.

- A name listed is only ever at its addresses: not looked up anywhere else, even if none of them answers. Case and a final dot don't matter.
- Their addresses go by the address policy as any other: a private network's only with `WEB_GO_PRIVATE`, this machine's never.
- Changing them (or the DoH choice) lets go of the connections kept idle (`goDNSChanged`), so the next request is dialled where the names are now; tunnels already open go on till they close.

## 4. Transport

One tunnel is one browsing context (`goroute.go`). The page opens it with the request `{"type":"go"}`; tabtopd starts an engine for it and answers `{"ok":true,"sandboxed":…}`, or fails with the reason (off, unavailable and why, too many tabs). The engine is killed when the tunnel closes, which also happens when the session ends or logs out and when the server stops. At most 3 engines run per session and 8 in all.

The page then sends JSON messages, each starting a new generation:

- `{"op":"navigate","url":…}`: HTTP or HTTPS with a host and no credentials; anything else is refused before the engine sees it.
- `{"op":"stop"}`.

History, back, forward and reload are kept by the page and sent as navigations. Phase 2 added `{"op":"event","gen":N,"kind":…,"id":…}` (addressed by node ID), `{"op":"dialog",…}` and `{"op":"resync","gen":N}`, and the replies `go-changes`, `go-url`, `go-dialog` and `go-file`; `goroute.go`’s header lists them all.

The server answers per generation:

- `{"type":"go-loading","gen":N,"url":…}`
- `{"type":"go-snapshot","gen":N,"url":final,"base":…,"title":…,"doc":tree}`, once the page’s document is ready (`Page.domContentEventFired`, or `Page.loadEventFired` if that comes first, after its `Page.frameNavigated`; what it does until it’s loaded comes as changes), at once for a navigation within the document, or after 30 s with what has loaded.
- `{"type":"go-error","gen":N,"message":…}`

Messages for a generation older than the newest are dropped on the server. Snapshot nodes are `{"i":id,"t":type,"n":name,"v":text,"a":[name,value,…],"c":[…]}`, read by the agent in an isolated world (section 6); the server leaves out scripts, `noscript`, templates, comments, doctypes, and every `on…` attribute, as defence in depth before the client’s sanitizer. A snapshot larger than 16 MB is an error, not a partial page. The page may send at most 64 KiB per message.

Run directories left by a tabtopd that died (each holds an `owner` file with its tabtopd’s process ID) are removed at start-up.

The broker (`goresource.go`) fetches images, stylesheets, and fonts for the renderer. They come over the tab’s own tunnel (`goprefetch.go`): `{"op":"res","rid":N,"kind":…,"url":…}`, answered by a `go-res` header (size and type, or an error) and the bytes in binary messages of up to 256 KiB that start with the request’s number, so they go between the tab’s other messages. A separate `go-resource` request, with a tunnel of its own, is used only while the tab’s isn’t open: a new tunnel is a WebSocket and a key exchange, which cost about 80 ms a resource on the same machine and several round trips on a distant connection, more than the fetch.

As soon as a page’s snapshot is sent, the server fetches ahead what the page shown will ask for: its stylesheets, `<img>` pictures and inline styles’ pictures, and what the stylesheets use (imports four deep, `@font-face` sources as fonts, other `url()` and `image-set()` as pictures, as `go-frame.js` takes them), at most 300 a page. They’re kept in the tab (64 MiB, the oldest dropped; failures not kept); a request for one being fetched waits for it. Measured on the same machine, from the snapshot to the page shown with its styles and pictures, first visits: Wikipedia 2.6 s → 0.4 s, www.sg 5.0 s → 0.1 s, GitHub 3.9 s → 2.4 s (most of it its 7.6 MB of CSS, rewritten in the frame).

The resource broker enforces:

- The same `fetch.go` client and policy as the egress proxy.
- Header filtering: never forward TabTop credentials, cookies, authorization, or proxy headers. Send a fixed, generic User-Agent.
- Compression: accept gzip, deflate, and brotli, decompress on the server, and enforce the limit on decompressed bytes. The client receives identity-encoded bytes.
- Per-request limits on time, bytes, redirects, and decompressed size, and at most 8 broker fetches at once across all sessions, 4 of them for one session (its others wait without holding a slot). Per-context byte limits are left to Phase 3.
- Accepted resource types: images, stylesheets, and fonts only.

### Cookies

The engine keeps cookies in memory for the life of its context only; nothing is persisted (no `--cookie-jar` or `--profile-dir`), and the cookie jar is destroyed with the engine. The resource broker sends no cookies. Decided for the first release: signing in to a site works within a tab (its cookies last while the tab does), and nothing persists across tabs or restarts; pictures, stylesheets and fonts behind a login don’t show. Persistent logins are not a goal for now. Never inherit TabTop’s authentication.

## 5. Rendering and sanitization

Use a dedicated frame document with `sandbox="allow-scripts"` only — no `allow-same-origin`, `allow-popups`, `allow-forms`, `allow-top-navigation`, or `allow-modals`. Its only JavaScript is TabTop’s trusted rendering agent; page scripts run only in the engine. See [iframe sandbox behavior](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe).

The frame CSP (a new constant, not `mdFrameCSP` or `directFrameCSP`):

```text
default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline' blob:;
img-src blob: data:; font-src blob: data:; media-src 'none'; connect-src 'none';
frame-src 'none'; object-src 'none'; form-action 'none'; base-uri 'none';
```

No network origin appears anywhere, so remote content cannot load except through the broker. Establish a private `MessageChannel` after validating the frame handshake.

Snapshots and mutations from the engine are untrusted. Before rendering:

1. Drop scripts, inline handlers, `javascript:` and other unsafe URLs, refresh directives, frames (an iframe’s page is drawn as a sanitized copy in a box instead, section 6), objects, embeds, `<base>`, and media elements.
2. Parse and rewrite CSS, including `@import`, `url()`, `image-set()`, and fonts.
3. Replace resource URLs with broker-backed `blob:` URLs, resolved against the document’s final URL.
4. Map engine node IDs to rendered elements, so events can be addressed back.

Apply the same checks to every mutation batch, not only the initial snapshot.

## 6. Interaction and DOM streaming

### Snapshot and mutations

- On each navigation, the snapshot is read by the agent (`goagent.js`) in an isolated world (`tabtop`), not `DOM.getDocument`, which leaves out whitespace-only text nodes (spaces between links went missing). The script numbers nodes in that world, so changes and events can use the same IDs, and reads forms as they are now.
- Changes come from a `MutationObserver` installed by the same agent (`goagent.js`) in the same isolated world, read in numbered batches; on a gap, an unknown ID or an oversized batch, the client asks for a full snapshot again. (Moli’s CDP DOM events carry CDP node IDs and skip whitespace nodes, so they can’t address the snapshot’s tree.)
- tabtopd polls for them (every 250 ms, every second once a page has been quiet for 10 s, and 300 ms after each thing the person does) instead of being signalled through a binding: in Moli 1.1.25, `Runtime.addBinding` with an `executionContextName` stops links within a page (`#fragment`) from navigating. Page scripts can neither see nor replace the agent.
- Moli emits no event for `history.pushState`; the agent’s batches carry the document’s URL, which the address bar follows. A fragment link emits `Page.navigatedWithinDocument`.
- Changes are serialized for the sanitizer, coalesced into batches, and subject to the per-context byte limits, since page scripts can produce mutations quickly.

### What the page observes (`IntersectionObserver`)

- `goobserve.js` replaces the page’s `IntersectionObserver` (with `Page.addScriptToEvaluateOnNewDocument`, before any of its scripts). `observe` and `unobserve` tell the agent, in its isolated world, by a DOM event on the element; the agent asks for those made before it started (as the page loaded) when it starts.
- The agent sends an observed element, with its options, once it’s one the shown copy has (snapshots carry them all, batches what’s new: `io` in `go-snapshot` and `go-changes`). tabtopd keeps only well-formed options (`goCleanIO`), at most 5,000.
- The frame observes the copy’s element with the browser’s own `IntersectionObserver`, which sees it as laid out and scrolled there, and sends what it sees, with the element’s box, its visible part and the root’s bounds as shown there (`{"op":"io","gen":N,"entries":[…]}`, in pieces of 500). Pages go by those places: YouTube loads a thumbnail only when its `intersectionRect` has a height, which the engine’s own 0×0 box for a picture it hasn’t fetched never has.
- tabtopd hands them to the page on the acts’ queue (callbacks may open a dialog), one handing over at a time, the newest per element kept meanwhile; the agent drops what repeats what was last handed over; callbacks run from a task of their own, as in browsers. It isn’t counted as the person’s doing, so a page that makes what it observes come and go can’t keep the idle watchdog off.
- Measured: YouTube’s channel page shows its thumbnails (18 of 35 pictures, those in view; none without). CNA, BBC News and The Verge load their lazy pictures either way. Sites learn which of their elements the person has scrolled to, as they would in a browser. A new observation reaches the person’s browser with the next batch of changes, up to a second on a quiet page.

### Sizes and scrolling (`ResizeObserver`, scroll positions)

- The engine's layout isn't the one shown: Moli lays YouTube's Shorts scroll box (`#shorts-container`) out 20 pixels high where it's 670 (its `scrollHeight` 20, where it's 6500), and keeps `scrollTo` within that. Shorts goes by those numbers: its reel height is `(scrollHeight − 2 × the first player's scrollHeight) / reels`, worked out when the box is resized (its `ResizeObserver`) or first scrolled, and the reel shown is `round((scrollTop − 16) / that)` on each `scroll` event. With Moli's, the height was −2.2 and every scroll a reel before the first; a swipe scrolled the copy, and the engine's page stayed on its first video.
- `goobserve.js` replaces the page's `ResizeObserver` too, the same way: what it observes is announced as `IntersectionObserver` targets are (with `s`, the box asked for; the same path, `io`), the frame observes the copy's element with its own `ResizeObserver` and sends the element's sizes there (`z`: client, scroll and offset width and height, the content box), also after each batch of changes and each scroll (what's in it grown, which no `ResizeObserver` reports), when they've changed. The page is given them: its callbacks (when the box watched has a new size, and, at most once a second per element, when only its scroll size has: a page that read it as it added to it, as Shorts does 100 ms after adding reels, read it before it got here), and, from then on, that element's `clientWidth`/`clientHeight`/`scrollWidth`/`scrollHeight`/`offsetWidth`/`offsetHeight` (getters on the prototypes, in the page's world only; the agent's world sees the engine's).
- Where an element is scrolled is where the person scrolled it: the agent sets it (`scrollLeft`/`scrollTop`, not `scrollTo`, which Moli keeps within its layout), says so to the page's world before the `scroll` event (`__tabtop_scrolled`), and the page reads that (`scrollTop` and `scrollLeft` likewise), and the event is sent each time the person scrolls (Moli may not have moved).
- The page scrolling an element itself (`scrollIntoView`, and `scrollTop =`, `scrollTo`, `scroll`, `scrollBy` on one whose sizes it reads from the person's browser, never the document's own: a place worked out from the engine's layout may be nowhere near the same there) is told to the agent (`__tabtop_scroll`, ignoring the agent's own scrolling, which an engine with shared worlds, Obscura, would report), sent with the next batch (`scrolls`, checked by tabtopd: at most 64, an element and a place within reason or a `block`/`inline` of `start`/`center`/`end`/`nearest`), and the frame scrolls its copy so. Where that ends up goes back as the person's scrolling does, even if it didn't move (a browser's page hears its scrolling: Shorts waits for that first `scroll` event before it takes the person's), but never a place the engine was last told, so a page asking again and again for where the copy can't go isn't answered again and again. Setting a place it's already at is nothing, as in a browser.
- Measured with Moli on YouTube's Shorts: the wheel, swipes and its "Next video" button each go on to the next reel, playing it at its size, through 24 in a row (three more lots of reels loaded). (Its arrow keys go the button's way in its script; not checked here.) Checked end to end with a page that goes by its scroll box's sizes as Shorts does, and scrolls it into view itself. Obscura (no layout of its own) passes it too; Lightpanda takes the first wheel turn but not the second (its scripted wheel, already short of a browser's).
- Shorts just loaded, its first scrolls: Shorts sets `shouldUpdateItemHeight` as it starts (its full-screen observer's first call), and the next `scroll` it hears once it knows its reels' height only works that height out again and puts its box at `index × height + 16`, not moving on; a job clears the flag. In Chrome that scroll is the one its own `scrollIntoView` of the first reel makes (measured: flag cleared at 5 s, the first wheel moved on). Here, two things made it the person's first scroll, so the first one or two after a load (the 20 s stall after a move to a fresh engine) went nowhere:
  - The frame told the engine where the box went only when that differed from where it last told it. The answer to the first `scrollIntoView` reached the page before its reels' height (its `ResizeObserver` job runs 1–2 s late in Moli); the next, after it, wasn't sent (same place). Now a place is told again once the element's new sizes have been sent (`resizedNow`, cleared as the batch goes; what's sent goes in order), so the page hears where it is with what it now knows.
  - Its `+ 16` is where this copy's snapping puts it back from (reel 0 snaps to 0): the frame told 0, Shorts set 16, about ten times a second, and its job to clear the flag never ran while it did (measured once for 5 s, every scroll ignored). The page asking at once (within 2 s) for the place it was put back from isn't told it went back again (`askedTo`): once, as in Chrome. Checked: a page that sets its snapping box 16 pixels down at each scroll it hears is told 3 times, not 31 in 4 s (`snapback.html`).
- Measured after: moved to a fresh engine mid-Shorts, the first scroll after the move went on (2 of 2 runs; before, never). Loaded afresh, a scroll in the first 12 s or so may still go nowhere: Shorts' own box is `overflow: hidden` from its `ResizeObserver` callback till its job (1–2 s in Moli, 100 ms in Chrome), and Moli's main thread was seen busy for 6 s as Shorts starts (a scroll made then shown at once here, taken by the page after).

### What the server's fetches for a page send: cookies, Referer (`goFrom`)

- What the server fetches for a tab's page (pictures, fonts, stylesheets, media) is sent what the page's own browser would send (`goFrom`, gocookies.go): the cookies for that address (from the tab's engine, `Network.getCookies` with its URL, SameSite against the page shown, as media's were), and, if the settings say (on at first: go/settings, "Send referring page information"), a Referer, by a browser's default policy (strict-origin-when-cross-origin): the page's address (without its fragment, user or password) to its own origin, its origin to another, nothing from https to http. Both are worked out again for each address a redirect goes to, so neither goes to a host it isn't for. A fetch with no tab to say whose page (a go-resource request on a tunnel of its own) is sent the jar's cookies any page may (SameSite=None) and no Referer; previews of files, neither, as before. The page's address is what's said for everything it loads (a browser says a stylesheet's for what the stylesheet loads).

### Media from servers without byte ranges (gomediadl.go)

- A server that answers a part with the whole file (200, not 206) was refused ("Media streaming requires a server with byte-range support"). Now the file is downloaded once (for the session and address), through the server, in order, to a temporary file (unlinked at once: gone when it's closed), with the cookies, Referer and user agent the parts would have had; parts are answered from it as they come, a part not come yet waited for (at most 60 s, then try again), a file whose size the server doesn't say waited for whole before its first part (the player needs its size). Changed meanwhile (its size or validator): said, as before. At most 512 MB a file, 2 at once a session, 8 in all; forgotten after 10 minutes unused. Ranges stay the way when the server has them; previews of files still refuse such servers.
- Checked: unit (sized and unsized, parts from anywhere in it, past its end refused, downloaded once, cookies sent; race detector); end to end, a video from a server that sends it whole plays, and a page's picture says the page (Referer), and doesn't with the setting off.

### A page's requests wait their turn (`goprefetch.go`)

- A tab answers 64 of its page's requests for resources at once; more were refused ("Too many resources are loading"), as were requests that waited 20 s for one of the server's fetches (8 at once, 4 a session). Now those over 64 wait their turn in the tab (up to 2000; more are refused), started as others finish, and a fetch waits up to 2 minutes for a slot. Leaving the page (the person's navigation, or the page's own) drops what's waiting its turn (each told "The page was left.") and ends the waits of what's being answered for it, so the next page's requests aren't held up behind them; fetches already going go on, kept for whoever asks next. Checked end to end: a page of 80 pictures, each sent slowly, has them all.

### Compression: Brotli, gzip, zstd, deflate (goresource.go)

- What the server fetches for a page's copy (pictures, fonts, stylesheets) asks for what Chrome does, as it says it (`Accept-Encoding: gzip, deflate, br, zstd`), and decodes each as it's read (`goDecoded`): Brotli (`github.com/andybalholm/brotli`), zstd (`github.com/klauspost/compress/zstd`; both pure Go), gzip and deflate (the standard library's; deflate zlib's, as HTTP has it, or bare, as some servers send and browsers take). Two may come one on another (`Content-Encoding: gzip, br`), undone last first; more, or any other encoding, wasn't asked for and is refused. The size limits are on what it decodes to, so a small file that decodes to a great deal is stopped at them; a zstd stream asking to hold more than 8 MB as it's decoded (HTTP's zstd limit, RFC 8878; Chrome's too) is refused. Media is still asked for in byte ranges, unencoded (`identity`).
- The engine asks for and decodes what it fetches itself: Moli asks `deflate, gzip, br` (no zstd, its own order), which can't be changed here (it would have to decode what came; the proxy sees only HTTPS's ciphertext), so its requests and the server's say different things.
- Checked: stylesheets in Brotli, zstd, deflate (both) and gzip-then-Brotli decoded; broken Brotli refused; Brotli, gzip and zstd bombs stopped at the limit; a zstd frame asking for a 64 MB window refused (and read, allowed it); three encodings, and `compress`, refused (unit); the test site sends its stylesheets in Brotli, the one imported in zstd, to who asks, and the pages are shown with them (end to end).

### Ad blocking (`goadblock.go`, go/settings)

- Off at first; turned on in Settings (☰ → Settings), which downloads the ticked filter lists (EasyList and EasyPrivacy ticked; Peter Lowe's and Fanboy's Annoyance offered; others added by address, at most 20, 10 MB each), through the server, from where the browser may go. - What's held to is what a host decides: `||host^` (with `$third-party`, `$domain=`, `$important`), `@@` exceptions (`$document`: nothing on that site's pages), hosts-file lines, a host alone. Rules for paths, kinds of request, or what pages show are counted as not used yet. A page's own host is never blocked, nor anything before the page is known: going to an ad's site loads it.
- Refused, as `goRefusals["ads"]`: by the engine's proxy (CONNECT and plain requests), for the page the tab says it's at (`setPage`: the top document as Moli asks for it, before it's fetched; the person's navigations; the frame navigated, when interception is off), and by the server's fetches for the page's copy (pictures, stylesheets, fonts, media, their redirects; and before the tab's resource cache, so what was let through while allowed isn't shown once blocked).
- Each site in Site controls has **Ads and trackers**: the browser default (on or off, Settings), Block (with ad blocking off, from the ticked lists, downloaded if they aren't), or Allow. The bar's shield says how many sites were blocked for the page (hosts, not requests: HTTPS through the proxy is named by host, and a picture's refused there and again for the copy), and opens the site's controls.
- Matching: rules kept by host in one hash map, a request looked up by its host and each domain above it, one lookup a label, every kind of rule for a host in one small entry (most rules a flag, not a rule kept); long `$domain=` lists as sets; the page's and host's sites (public suffix list) worked out only if a rule asks; what's decided kept by host and page for the set of rules (16k at most). Measured with 65k rules (`goadblock_bench_test.go`): a decision 1.3 µs and 6 allocations → 260 ns and none, 75 ns cached; reading 60k rules 45 ms and 22.7 MB → 29 ms and 9.4 MB.
- Elements hidden: `##sel`, `site##sel` (with `~site`), `#@#` exceptions, `$generichide` and `$elemhide` (and `$document`) on a site's pages. In the page's copy, each selector a rule of its own, `display:none !important`, in a constructed stylesheet the page's changes can't remove (`document.adoptedStyleSheets`); `insertRule` takes one rule only and throws on what this browser doesn't know, which is left out, and the server sends only plain selectors (no braces, `;`, `@`, escapes, comments, `url(`, `<`, or extended syntax such as `:has-text(` or `+js(`, which are counted as not used). Lists have tens of thousands (EasyList and EasyPrivacy: 23,462), nearly all for a class or an id, so they're kept by the first class or id in their first compound (`ins.adsbygoogle`: `.adsbygoogle`) and a page is sent only those for the classes and ids it has: with its snapshot (`hide`), and with each batch of changes that brings new ones (the classes and ids of the nodes it adds and the attributes it sets), each selector once a page; with the 427 that need neither and its site's own. A page with 300 classes and ids, some ads', is given 430, worked out in 0.12 ms. Embedded pages' copies (iframes) are drawn as boxes of their own, which rules for `iframe` don't match.
- By address (`||ads.example/serve/`, `/banner/*`, `&adunit=`, with `$script`, `$image`, `$xmlhttprequest`, `$subdocument` and the other kinds, `~` before one, `$third-party`, `$domain=`, `$match-case`, `$important`, `@@` exceptions): held to where the whole address and kind are known. The engine's requests: Moli pauses every one (`Fetch.enable`, `urlPattern: "*"`); documents go on through the tab's event loop as before (an embedded page's document refused, as `$subdocument`, by `Fetch.failRequest` with `BlockedByClient`), everything else is taken off the CDP reader as it comes (`cdpConn.paused`) and answered at once in a goroutine of its own, so pauses never wait behind the tab's other events. Moli doesn't fetch pictures (the copy's are the server's), so pictures, stylesheets, fonts and media are held to the same rules in the server's fetches for the copy, as image, stylesheet, font and media. The proxy, which sees HTTPS by host only, still refuses whole hosts, but not those with exceptions by address (`@@||cdn.example/ok.js`), which would undo them; if interception is turned off for a tab (its queue full), the proxy's blocking by host is what's left. Spike (`TestGoAdMoliInterception`, real Moli): Moli pauses scripts, stylesheets, XHR and fetch with their kinds, and a request failed is never asked of its site; `Network.setBlockedURLs` works too, but holds requests to `*` patterns only, too plain for lists' options. Rules are kept by a word their pattern needs ("banner" in `/banner/*`): of those, the one fewest rules have (counted once all are read, indexed when first asked of), and a request's address is split into words and only those words' rules tried; a rule's pattern is looked for from where its leading text is (`strings.Index`), not at every place. With the real lists: 11,665 rules by address on 8,761 words, at most 31 a word (351 when kept by the longest word), 15 tried for every request; a request decided in 3.1 µs (7.2 µs before). Usable rules 130,987, not 4,149 (regular expressions, scripts run in pages, options that change requests: `$redirect`, `$csp`, `$removeparam`...). The shield counts what's refused: a host refused whole, or an address.

### A tab kept while its connection's lost (`goresume.go`)

- A tab outlives its connection: its engine, its page and what the page does (timers, a video, a feed updating) run on for 5 minutes (`goDetachedFor`) after the connection goes (the network dropped, the phone slept, the page reloaded), and a connection that brings the tab's token, from the same login session, takes it back as it is. A file or stream download started from that tab keeps it available beyond the five minutes until its last download finishes, fails or is cancelled. The download also counts as activity for the login’s idle timeout.
- A tab runs on a goroutine of its own (`runGoTab`: its engine, its cookies' start and end, the cache's pruning), from its first connection till it ends; a connection's handler only lends it the connection (`goLink`) till that goes, then returns, so the session's count of open connections isn't held by a tab no one's connected to. What the tab sends while no one's connected is dropped (`goConn`): a connection taking it back is sent what's there now (`resume`): the page loading (its snapshot follows as it would), or the page shown, read whole as the same document again (a copy still shown keeps its place and what's typed in it; a new one, after a reload, starts where the page in the engine is scrolled: snapshots now say, `at`), and a dialog or pop-up it's asking about. Nothing shown (its load failed, or it was a file): the page loads its address again (`go-reload`), unless it took the tab back with a load of its own (an address entered, or a certificate warning's Continue, while not connected), which isn't replaced by that.
- A page being left (reloaded, or another loaded) doesn't reconnect as its connection closes: it would, with the token the next page (the same browser tab's sessionStorage) has just been given, and take that page's tab from it ("This tab was opened in another window"). Back from the browser's cache, it reconnects.
- Connected again however it comes (the banner's own try, an address entered, the tab shown again, back from the cache), what said the connection was lost goes at once: the "Connection lost" banner (`reconnected()`, reconnect.js; it had stayed till its next try, up to 30 s later, the page shown and working under it) and the "engine was closed" notice with its Reconnect. The terminal's banner the same. An address entered while not connected is gone to once connected, a tab taken back as it was too (it had shown the tab's page, the address dropped). Checked end to end: the page's sockets closed and its tries refused till the next is 5–8 s off, an address entered: the banner gone within 3 s, the page loaded.
- One connection at a time: a page's connecting while one is open or opening is the one (`connect`), and a connection closing that isn't the page's now (replaced) touches nothing of the one that is, nor says anything. Before, a page used as it loaded could open two, the second, with the token the first was just given, taking the tab from it ("This tab was opened in another window"): the cookie check's new tab showed it, now and then, in CI's and here.
- The token: 128 random bits, given with the tab's acceptance (`resume`), kept by the page in sessionStorage by tab (`tabtop-go-resume[:N]`: a reload brings it, another browser tab doesn't), and sent with the `go` request (`resume`). It's only good with the session that opened the tab: another session's connection with it gets a new tab. A connection taking a tab another still has (a browser tab duplicated, or the old connection not yet seen to be gone) takes it: the other's told (`go-taken`, and closed with why), and forgets the token, so it doesn't take it back in turn.
- Ended at once, not kept: closed by the person (a tab of the tabs' page closed: it says `close` first, and doesn't reconnect as its connection closes), its engine stopped, or its session ended (logged out, its time up, ended from another, or idle: `goSessionEnded`; a session with nothing open ends after `WEB_SESSION_IDLE`, 1 hour by default, so a server set to less than 5 minutes keeps tabs no longer than that). A kept tab still counts against the engines a session may have (6) and the server's (12); at the limit, a new tab takes the place of the session's tab without an active download let go longest ago (a page closed, not just cut off, is kept too: there's no telling), as it would have closed at once before.
- Taken back promptly whatever the old connection's state: a connection taking a tab tells and closes the one it had aside, not holding the tab up; one the tab doesn't take within 3 s (held up writing to a connection gone without a word, which gives up only after a minute) has that connection cut, and gives up after 15 s; and the page, told it's taken back but sent nothing within 10 s, starts a tab of its own and loads its page again. A page that went elsewhere while no one was connected comes back as a page of its own (an entry in the history), not as the same document read again.
- Checked: a tab whose connection goes is kept, taken back by its token from its session and not from another's, and ended by `close`; one not taken back ends; one taken from an open connection tells that one (unit). End to end: the page reloaded comes back with what was typed in its field, where it was scrolled, its count gone on, not restarted; its connection cut for a few seconds, the count went on meanwhile, and it's taken back with its field and place.

### A tab moved to a fresh engine at a soft memory limit (`gobrowser.go` `recycleSoon`, go.js `maybeSwap`)

- Why: Moli keeps elements a page has removed. Scrolling YouTube Shorts, its resident memory grew about 20 MiB a minute (252 → 546 MiB in 15 minutes) while its JS heap stayed at 33–38 MiB and the DOM at about 2,900 nodes, so the watchdog's 1 GiB would kill the tab after about 40 minutes.
- /go's own references let go first (part A): the agent's element ids (`byId`, WeakRefs), what it watches, observes and has adopted are swept of elements no longer in the document every 30 s; `goobserve.js` parks an `IntersectionObserver`/`ResizeObserver` target that's been out of the document for three 10 s looks (a WeakRef, taken back and announced again if it returns); the frame unobserves its copy's elements gone for three looks. Measured: 20.3 MiB a minute against 21.2, so the engine's retention is nearly all of it.
- The move (part B): the watchdog stores each engine's resident memory; once it's been past 60% of the limit (`goRecycleAt`) for 10 s (`goRecycleAfter`: Shorts passes a lowered mark for a moment as it loads, then settles), the tab tells its page once (`go-recycle`; again when a connection takes the tab back). The page, at the next address its page goes to (a reel changing its address, a link, an address entered), opens a second connection (`replaces`: the old tab's token; the server saves the old engine's cookies first, so the new one starts with them; a private tab's stays private), loads the address there, and keeps what it's sent. When its first snapshot arrives, the page switches to it, the old tab is closed (`close`), and its engine is ended. If nothing arrives within 60 s, the second connection is dropped, and the page loads the address on the old tab, if the person asked for it.
- Not while something's under way: a download, a file being staged, a chooser, a drop, a paste, notification or pop-up question, the device or certificate sheet, an open dialog, or a key or input in the last 10 s; at most once every 5 minutes per page. What's lost: the old page's script state (a player's place in its video, what's typed in a field not yet sent), as on a reload; its cookies are kept (site storage not checked).
- Checked end to end (`go-check`): moved at the next address after `go-debug-recycle` (only with `goDebug`), the page fresh there, a cookie and a `localStorage` value set just before kept, the tab's own engine ended; not moved while typing, or while a download runs, and moved once it's done; a private tab's sign-in kept. Unit (`TestGoRecycle`): not advised under the mark or for a moment past it; advised once past it for 10 s, and again to a viewer connecting again.
- On Shorts, the mark lowered to 32% (328 MiB) and nothing forced: 10 minutes, 56 shorts, two moves (the second 5 minutes after the first, at 352 MiB, back to 261 MiB); the engine never past 367 MiB. Each move lands at the next reel, which plays. The first scroll after a move went nowhere at first, as after any fresh load of a short; fixed since (see Sizes and scrolling: Shorts just loaded). Twice the video was gone from the copy for about 20 s after a move.

### What it says it is (`gouseragent.go`)

- A tab's engine says its own user agent (Moli's: Chrome on Windows, `Browser.getVersion`). On a phone (a touch screen whose shorter side is under 600 pixels; a tablet's isn't), it's Chrome on Android, set before what's loaded next (`Emulation.setUserAgentOverride`): the user agent as Chrome gives it (`Mozilla/5.0 (Linux; Android 10; K) … Chrome/<the engine's major>.0.0.0 Mobile Safari/537.36`), `navigator.platform` `Linux armv81`, and client hints (`Sec-CH-UA-Mobile: ?1`, platform Android 14, model Pixel 8, the engine's full version), all one phone's; measured with Moli (headers, `navigator`, high-entropy hints, on later loads too). The **Desktop** menu checkbox reloads the current page with the engine’s desktop profile and applies to later requests in that tab. Unchecking it restores automatic device detection. Obscura takes the user agent, but its `navigator.platform` and client hints still say Windows (as its own default already disagrees with itself).
- What the server fetches for a page (pictures, fonts, stylesheets, media) says what its tab says; asked on a tunnel of its own, what the session's tab last said, or an engine's own desktop one. It never says TabTop (it was `Mozilla/5.0 (compatible; TabTop remote browser)`).

### Cookies, kept (`gocookies.go`, go/cookie)

- An engine has no profile: what a site set (a login) was gone with the tab. The account's cookies are kept in a jar on the server, sealed (XChaCha20-Poly1305) in `-go-cookies-file` with the key in `-go-cookies-key-file` (the image: `~/.config/tabtop/go-cookies.sealed` and `go-cookies.key`; either empty: in memory, till a restart). A file that can't be opened is set aside, not overwritten, as the share links' is; both are kept out of the file roots, as the gateway's other state is. Session cookies (no expiry) are kept in memory only, as a browser keeps them till it's closed, but a kept site's are saved too (Keep, below). At most 3000 cookies and 2 MB of names and values (the least lately changed go first, a kept site's after every other's), 4 KB a cookie.
- **Keep** (a site's page in Site controls, "Keep cookies and site data"; `go-settings-set` `keep` / `keep-off`, by the site, its subdomains too; `keep` in `go-sites.json`, deleted with the site's other settings): for sites whose sign-ins should last (a social network, say). A kept site's cookies and saved storage are spared by every clear by time, all time too (`goForgetRange.spare`: the jar, the saved storage, and the open tabs' cookies, storage and data alike; the storage it changes meanwhile still taken in); its session cookies are saved with the jar's others, so a sign-in lasts a restart; and, over the jar's or the storage's limits, it's the last to go. Cleared by name (its own Clear data, or selected among others) it's cleared: the dialog says it's kept. All sites marks it ("Data kept"); Select's choices and Invert pass it by (a tap of its own selects it); the time-range dialog names the sites it spares.
- A tab's engine is given the jar's cookies before it loads anything (`Network.setCookies`, by a URL of the cookie's host and path, its domain only for a domain cookie, so a host-only one stays host-only), and what it kept is read back: that's what its later reads are compared with. Its cookies are read (`Network.getAllCookies`) after each page it loads, every 15 s, and as it closes; what changed since its last read is taken, never its whole state (a tab still holding a cookie cleared elsewhere doesn't put it back), and a cookie it no longer has is removed only if the jar still has it as that tab last did. When a cookie was set (or its value changed) is the jar's own (CDP doesn't say; a renewed expiry isn't a change), for clearing by time.
- `go/cookie` (go-cookies.html, go-cookies.js; the ☰ menu's "Cookies and site data", in a tab of its own) lists the sites (registrable domains, `golang.org/x/net/publicsuffix`) with cookies kept or data in a /go tab open: how many cookies and when last set, never a value. A site can be deleted, or what sites set in the last hour, 24 hours, week, month (30 days), 6 months or all time cleared (all time asks first); tunnel requests `go-cookies` and `go-cookies-forget` (`name`: the site; or `within`, seconds), which need no engine. What's cleared is removed from the tabs open too (`Network.deleteCookies`), with the site's other data (local storage, IndexedDB, caches: `Storage.clearDataForOrigin`, not its cookies, the jar's to remove), for a site, its origins the tab has been to; for a time, the origins it went to since. Moli also keeps top-level localStorage as described below.
- Media the page plays, fetched by the server (go-media.js's ranges), is sent the cookies the site's own browser would send it: over the tab's tunnel, the engine's cookies for that address now (`Network.getCookies` with its URL: its sites' latest, httpOnly ones too), those a request from the page shown may carry (SameSite Lax, Strict or unsaid only from a page of the same site; None, with Secure, from any), the longest paths first, at most 8 KB; asked again for each address a redirect goes to. Asked on a tunnel of its own (no tab), the jar's, matched as a browser matches them (a host-only cookie to its host alone, a domain cookie to subdomains, by path, Secure over https), SameSite=None alone. Pictures, fonts and stylesheets are still fetched without cookies.
- Obscura says a domain cookie's domain without its dot: one the jar has with the dot is taken as the jar's, an unknown one as host-only (sent to less, not more); its `Storage.clearDataForOrigin` clears nothing (measured), so only its cookies are cleared. The resource broker (pictures, fonts, media fetched for the copy) sends no cookies, as before.
- Checked end to end with a page that sets a cookie and says what it was sent: kept for a new tab, deleted by site while a tab is open (gone from it), listed at go/cookie, and the last hour's cleared there (gone from a new tab); the jar's merging, clearing by site and by time, sealing and setting aside by unit tests.

### Site storage kept

Moli keeps top-level HTTP(S) localStorage by origin in `-go-storage-file`. The image uses `~/.config/tabtop/go-storage.sealed` and the cookie key, with a separate encryption context. An empty storage path keeps it in memory. The limits are 5 MiB per registrable site and 50 MiB in total. The least recently used sites are evicted first.

Moli pauses document requests, including redirects, while TabTop installs an origin-checked document-start script. It fills missing entries on the first visit to an origin in each engine. Change events merge by key, and an orderly tab close compares a final read against the tab's known state. Moli keeps cross-site frame storage partitioned within the engine. IndexedDB, Cache Storage, service workers, and sessionStorage also stay in the engine.

Cookies and site data shows stored bytes and item counts. Delete clears a site's saved and live localStorage. Time-based clearing selects whole sites by when their saved localStorage last changed.

### Private tabs (`goincognito.go`)

- A tab opened as private (the strip's incognito button, a hat and glasses, beside +, the phone's list's **Private**, or the ☰ menu's **New private tab**) keeps nothing of where it went. The tabs' page tells it before it starts (`tabtop-go-private:N` in sessionStorage, never in the frame's address, which stays `tab?id=N`), and it asks the server for one at each connection (`go` with `private`), so a new tab made for it (an engine restarted, a token gone) is private too. The server's `goTab` holds whether a tab is private: a token takes back only a tab of the same kind, and both acceptances say which it is.
- Its engine is started without the shared HTTP cache (`goEngineConfigFor`: no `--http-cache-dir`, no `/cache` bound). Its own cache and the engine's cookies and IndexedDB stay in memory or in its sandbox's `/tmp`, and go with it. It isn't given the account's cookie jar or saved localStorage, and adds nothing to them. A session's private tabs share a jar and a storage of their own instead (`goPrivates.privateFor`: `newGoCookieJar("", "")`, `newGoStorage("", nil)`), so a sign-in holds across them, and in a window one of them opens, which opens private. Both are emptied and dropped when the session's last private tab ends: closed, not taken back within its 5 minutes (or, with a download running from it, once that's done), or its session ended. Closing the browser tab rather than the private tabs therefore leaves them, and their cookies, on the server for those 5 minutes. **Restart remote web engine** reaches private tabs too (every tab in `goTabs`, not only those the account's jar lists, as **Clear cached files** now does as well), and keeps their jar and storage for 30 s (`goPrivateKeep`) for them to come back to.
- Site controls doesn't see them. Their visits are the private jar's tabs', not the account's, so no site is listed, marked visited or counted from one. Clearing data from Site controls doesn't reach them either.
- What the server fetches for a private tab's page (pictures, fonts, stylesheets, media) is sent its own engine's cookies. On a tunnel of its own (`go-resource` with `private`), it's sent none rather than the account's SameSite=None ones (`goFromNoTab`). A media download made for one is kept apart from the session's other tabs' downloads (`goMediaKey`).
- On this device: no recent sites (`recent` and the start's list), no page title in the device's history (the tabs' page's title is "Private – Browser"), and a pop-up's answer isn't offered to be remembered (nor kept by the server if asked: `popup-answer` from a private tab). Not done (a known gap, kept for reloads): the tab's pages back and forward, addresses included (`tabtop-go-kept:N`, `tabtop-go-history:N`), and its resume token stay in sessionStorage, as any tab's do, so a reload carries on. They're this browser tab's alone and removed when the private tab is closed, but a browser that restores a closed tab or a session restores its sessionStorage, and these with it.
- Still as in any tab: site settings (blocked sites, ad blocking, pop-up and media defaults), downloads saved into Downloads (and the activity log's record of them), the server's address as sites see it, and the account's DNS settings. Its start page says so. It is marked by a violet edge, and by the hat and glasses in the strip and in place of its Back button's arrow (still Back, named so).
- Checked: unit (`TestGoPrivateJar`: the session's own jar and storage, not the account's nor another session's, in memory, kept while any private tab holds them, emptied with the last, a restart's 30 s; `TestGoPrivateEngineConfig`; `TestGoPrivateFromNoTab`: no account cookies for a private tab's own-tunnel fetch, its media kept apart; `TestGoTabsBrowsers`; `TestGoRoutePrivate`, through the route: a private tab told so and given the session's private jar, not the account's; a token taking back only a tab of its kind; private tabs sharing the jar; the jar let go with the last); end to end, go-check's "private tabs" step (the account's cookie not sent in a private tab; its own sign-in sent in a second private tab made from its menu and in a window it opens, a private tab (its pop-up question, when asked, with no Remember offered), but not in the account's tab nor listed in its jar; no recent site kept; the page's title not naming it; a new private tab, after all were closed, with no cookie; still private after the tabs' page reloads).

### Touch: a swipe isn't a tap (`goinput.go`)

- A finger was given to the engine as what's under it (an element, and where within it). A swipe scrolls the copy under the finger, which stays over the same thing, so the engine was given a finger that hardly moved, and made the swipe a tap: a click on what it started on (sometimes: as the scroll reached the engine before or after). Now each finger goes down on what's under it, then moves as it moves on the person's screen (the frame sends where it is there, `cx`/`cy`; the engine's window is the copy's size), so the engine sees the swipe a swipe (and a page's own swipe gestures see its whole way); and a flick quicker than its moves are sent is given where it ended. Checked end to end: swipes over buttons, the copy scrolling under the finger, slow and quick, click nothing; a tap clicks once (without the change, swipes clicked).
- And the moves before a finger's let go are given first: the server keeps a finger's (and the mouse's) newest move till the engine's ready for it, and a finger let go before it was had that move dropped, so on a slow engine a quick swipe's only move was lost and the swipe was a tap again (CI's slower machine showed it). Now a press, a release, a finger down or let go, or a drop is queued after the moves waiting, in order (`movesFirst`).
- A finger on a player (laid over the page, go-media.js) scrolled the copy under it, but the engine's page was never touched: a page that swipes by its own script, with nothing to scroll (YouTube's Shorts on a phone: its reels in a box that hides its overflow, moved by its touch handlers), didn't go on. Now a finger dragged over a player is also a touch for the page, on what's under it, down, moving as it moves, let go; a finger not moved is the player's tap (its controls), and the page's touch is cancelled (`touchCancel`, no click of the engine's own: Moli makes none for it). Checked on m.youtube.com/shorts on a phone's screen (a swipe went on to the next), and end to end with a page that swipes its reels by script, a video over each: a swipe over it goes on; a tap is no click or swipe of the page's.

### Embedded pages (iframes)

- An iframe is drawn in the copy as a box of its own (a shadow root, sized from its `width` and `height`, the page’s `iframe` rules rewritten to `[data-go-iframe]` so they apply to it), its page copied into it and sanitized as the page is. Pointer and keyboard events are routed to the engine frame by its own node IDs; the copied page’s scripts run only in the engine.
- A frame of the page’s own origin (or `srcdoc`) is read by the agent in the page’s world, into the snapshot, as a document node (`t: 9`, with its base, checked as an http(s) address) under its iframe; its changes resend it whole.
- A frame of another origin, which its parent agent can’t see into, is read in an isolated world of its own (`goframes.go`). The CDP frame tree is walked through three iframe levels (`goFramesDepth`); each frame is matched to its owner in the parent document (`DOM.getFrameOwner`, `DOM.resolveNode`, then the parent agent’s node ID). New, navigated or changed documents are sent whole. Nested updates name the chain of owner IDs and document identities, so input is evaluated in the right frame and stale documents are rejected. Slow or oversized frames remain isolated; the existing limits are 4 MB sent per second per tab, at most 16 frames per page, 2 MB per document and a backoff of up to 8 s for frames that keep changing. Stylesheets and pictures are fetched against each frame’s own base.
- Cross-origin frames nested three deep are shown and interactive. Frames deeper than three levels aren’t discovered. A Cloudflare or other challenge can be displayed and interacted with, though completing it is up to the person. `TestGoNestedFramesWithMoli` covers nested rendering and routed clicks.

- A press in an embedded page's copy goes to its page, by the frame's own node number and the chain of iframe owners enclosing it. Clicks, pointer moves, wheel input, taps, typing, keys, focus and form submission follow that route; the server checks each parent document identity and runs the action only in the target frame's world. A frame refresh updates its own copy without replacing its containing copy. A tap is a press and release, not a touch, since the engine places a touch by the iframe's box and the copied frame's coordinates differ; a swipe scrolls the copy, and drops into frames are not supported. An iframe's `scrolling="no"` hides its copy's scroll bars (still scrolled by wheel and finger) and `frameborder="0"` hides its border. Refreshes preserve focus and unsent typing for the same document; actions for a replaced document are dropped. These behaviors apply through three iframe levels.
- In an embedded page's copy its html is in a box, where selectors with something before an html (`* html`, `*:first-child+html`: old Internet Explorer's hacks, which match nothing in a document) would match: they're dropped from every stylesheet, and a rule left with none. reCAPTCHA's checkbox had been drawn under its label (`* html .goog-inline-block { display: inline }`).

### Canvas2D snapshots

Canvas elements are rendered as actual canvases in the sanitized copy. A document-start hook tracks canvases that obtain a 2D context and watches pixel-changing Canvas2D calls. The agent asks for a PNG only during a document snapshot or after a dirty notification, then sends the bounded image through the existing change stream. The server accepts only decodable PNGs within the canvas dimension, pixel and byte limits; the viewer accepts base64 PNG data only and draws it into the copied canvas. Drawing stays in Moli, so page scripts, input and Canvas2D readback continue to use the real page canvas.

This is image replication rather than API remoting. It supports ordinary Canvas2D drawing and updates, but the viewer does not reproduce the page's drawing context or readback APIs. Cross-origin-tainted canvases cannot be read through `toDataURL` and show a protected-pixels note. Oversized or unsupported canvases show an unavailable note. Animated canvases are bounded to three dirty canvases per change batch; a busy canvas may therefore lag behind the source. `OffscreenCanvas` and worker drawing are not covered by this path.

### Certificate errors

A page whose HTTPS certificate isn't trusted (expired, self-signed or from a private authority, for another name) isn't shown. TabTop shows a warning of its own instead (`go-cert-warning`, go.js `certWarning`), in its own chrome, never the site's page: the reason (from the engine's `net::ERR_CERT_*`), what the certificate says (whom it's for, who issued it, until when, its names: read by tabtopd on a connection of its own that verifies nothing and closes, `goCertProbe`), and **Go back** or **Continue to … (unsafe)**. Both a load the person asks for (`Page.navigate`'s error) and one the page makes itself (its document's `Network.loadingFailed`) are caught; other failures keep their messages.

Continue (`cert-continue`, only for the host and address just warned of; pressed while the connection's lost, sent once it's back, the tab taken back as it was; on an engine that can't ignore certificate errors, the exception's taken away again and the warning says it can't) makes the host an exception for the tab (`goCertExceptions`, gocert.go): kept in memory, gone with the tab, at most 64. Then:

- **The engine** is told to ignore certificate errors (`Security.setIgnoreCertificateErrors`, on the tab's own session) while the tab's page is on an excepted host, and only then: it's set as each load starts (the page's own document's request held till it is, so what that page loads goes by its host, not the last page's) and each document commits. Moli can't decide request by request (it sends no `certificateError` events).
- **The proxy** therefore lets the engine reach no other host by a tunnel meanwhile, whatever the port (`goProxy.tunnel`, `refuses`: `cert`); plain HTTP still goes. Port 443's tunnel is refused at once; port 80's by its first byte, TLS's (`0x16`: `https://host:80/`) refused and anything plain let through, so a page's `ws://` WebSocket works meanwhile. Another host's certificate can't be checked on the engine's own connection without intercepting it, and a check on a connection of tabtopd's own proves nothing about the engine's next one (an attacker on the path can let the one through and not the other), so none is made for trust. (Revocation is looked up so, below: a refusal it can only add, never a certificate it lets through.) So what the engine ignores is the excepted hosts' only; nothing's intercepted (no TLS bumping, no CA of TabTop's). The cost: on an excepted page, what the engine itself loads from other sites over HTTPS (a CDN's script, another site's frame) isn't loaded; TabTop's own fetches (pictures, stylesheets, fonts) still are, checked. A page the excepted page goes to on another host (a link, a redirect), so refused, is loaded again at once with certificate errors heeded (`certFailed`), and warned of if its certificate isn't trusted either.
- The flag the proxy goes by is set before the engine's told to ignore errors and cleared only once it's been told not to: a call to the engine that fails or times out leaves the proxy refusing.
- **TabTop's own fetches** for the tab (its pictures, stylesheets and fonts, media, Save stream and downloads) use the tab's own client (`goFrom.client`): no check for an excepted host, the full check for any other (redirects too), on connections not shared with other tabs. A host that's an address is checked by the address dialled (no name is sent in TLS for one).
- The engines' shared HTTP cache (`gocache.go`) doesn't carry an exception's responses to other tabs: Moli (1.1.25) doesn't serve a response fetched with certificate errors ignored to a tab heeding them, though it serves the same script fetched without errors from one tab to the next (checked in `go-check.mjs`).
- A later load of an excepted host (a link) goes straight there; the address bar's site button says it's not secure: "its certificate isn't trusted (an exception, this tab)", and Site controls says "Certificate not trusted", not "Secure".

Checked end to end (`test/go-check.mjs`, the test site served over HTTPS with a self-signed certificate): the warning and its details, Go back, Continue (the page and its picture shown, the site button marked), another page of the excepted host without a warning, and a link the page follows to another untrusted site warned of. `TestGoCert*` covers the error's words, the probe, the tab's client (an exception's host taken, others and the shared client not; an address's), the proxy's refusals while the engine ignores errors (any port, the exception's host let through, plain HTTP), a failed call to the engine leaving it refusing, and the tab's client bounding its TLS handshake.

### Revoked certificates (`gorevoke.go`)

Neither Moli (no revocation checking; and nothing over CDP of the certificate a connection of its got: no `securityDetails`, `Network.getCertificate` unknown) nor Go's TLS checks revocation, so a site whose certificate its issuer had revoked was shown as secure (revoked.badssl.com: Let's Encrypt's, in its CRL). Chrome (CRLSets) and Firefox (CRLite) refuse it, with no way past.

- Before the engine's tunnel to an HTTPS host is spliced, tabtopd reads the certificate the host serves on a connection of its own (as `goCertProbe` does), in parallel with the tunnel's own dial; if its chain verifies, its serial is looked up in the CRL it names (or a stapled OCSP response, if one comes). Revoked: the tunnel's refused (`revoked`) and TabTop's certificate warning is shown, for an address entered and a page's own navigation alike ("Its certificate has been revoked by its issuer: it may have been stolen, or issued wrongly"; Problem: revoked by its issuer), with Go back and Continue, as for a certificate not trusted: the person decides (Chrome and Firefox don't let them). Continue makes the host an exception for the tab, for its revocation alone (`goCertExceptions.revoked`): its tunnels and TabTop's own fetches from it aren't refused, and the engine isn't told to ignore certificate errors (it has none of its own for it), so other sites' HTTPS isn't refused meanwhile, as it is for an exception the engine needs. TabTop's own fetches for the browser (`goClient`: pictures, stylesheets, media, downloads, filter lists) check the connection's own certificate the same way (`VerifyConnection`).
- No key pinning, as Firefox: a site's own pins (HPKP) are gone from every browser, and what's left is Chrome's private list compiled into it (Google's domains, and pinning-test.badssl.com pinned to a key it doesn't have, so only Chrome refuses it). pinning-test.badssl.com's certificate is valid and trusted; it opens here, as in Firefox (decided, November 2026).
- What it proves: whether the certificate the host serves tabtopd is revoked, not the engine's own connection's (an attacker on the path could serve each differently); it catches a site serving a revoked certificate. A certificate not trusted isn't its business (the engine's warning is).
- Soft-fail, as browsers: anything but an answer allows (no CRL named, one unreachable, over 16 MB, not signed by the certificate's issuer, out of date, or another distribution point's, a sharded CRL's other part, by its issuing distribution point). No live OCSP (asking a CA's responder tells it each site visited). CRLs are fetched through the address policy (where the browser may go, ports 80 and 443), kept till their next update (a day at most, 64 of them); a CRL address that didn't answer isn't asked again for a minute (a CA's CRL server down would otherwise stall each new host's tunnel, and each new connection of TabTop's own, 8 s each); a host's answer 10 minutes (a minute with no answer); one check a host at a time; a tunnel waits 8 s at most. A failed load is warned of as revoked only if the proxy refused that tab that host for it (`refusedRevoked`, `tookRevoked`: a note's good for 30 s, the oldest let go first past 64, so a picture's never crowd out a page's), not because the host was found revoked lately: once continued to, the host's other failures are said as they are; a typed address that redirects there is warned of at where it went. A CRL's fetched on its own time (8 s), not its asker's: an asker out of time (a slow host's handshake) gives up, the CRL's still kept for the next, and only a server too slow or failing has it taken as down. The CRLs kept come to a million revoked serials at most, all together.
- Cost, measured on first visits (a fresh engine, November 2026): Wikipedia's main page 2.0–2.2 s with it, 2.0–2.4 s without; BBC News 4.6 s and 4.6 s with it, 2.3 s and 4.2 s without (the network's spread larger than the check's). revoked.badssl.com refused in about 1 s.
- Checked: unit (a test CA, its CRLs from a test server: listed, revoked; not listed; its own distribution point's; another's; signed by another key; out of date; not a CRL; unreachable; on a port the browser doesn't reach; none named; kept, not fetched again; an untrusted chain left alone; a CRL at an address the policy refuses not fetched; TabTop's own fetches refuse a revoked connection and take one that isn't); an exception for a revocation alone isn't one the engine ignores errors for; by hand, revoked.badssl.com warned of, typed and by badssl.com's own link, and loaded once continued to (the site button: not secure, an exception).

### WebGL canvas remoting

The goal is to show the pixels of a page's WebGL canvas in the sanitized copy, while keeping the page running in the server-side engine. The viewer replays a bounded stream of graphics operations into its own WebGL canvas. This is display remoting: it does not make the viewer's GPU or pixels available to the page. WebGPU and direct transfer of GPU resources are out of scope.

[Clearcote's Canvas Bridge](https://github.com/clearcotelabs/clearcote-browser/blob/main/docs/CANVAS-BRIDGE.md) is a protocol and implementation reference, not a drop-in dependency: its engine hooks target its Chromium build and its bridge is primarily designed for canvas readbacks. The repository's code and patches are BSD-3-Clause; preserve its notices if code is reused.

The page continues to call its WebGL1 context in Moli. `gogl.js`, installed before page scripts, records calls from a fixed allowlist and signals after clear, draw and upload operations. Where this Moli build lacks an allowed WebGL1 method, the hook supplies a bounded compatibility stub so page code can continue and the viewer can replay the call. Missing WebGL1 and WebGL2 constants are filled with their standard enum values; missing limit queries get conservative values and state queries use tracked bindings. This keeps those calls out of Moli's incomplete renderer, so source-side readback and exact GL state remain limited. Snapshots carry a full replay log; regular updates carry only new calls over the ordered `/go` change sequence. The server keeps, per canvas, the object IDs and extensions the log has created so far (`goGLStream`), and checks each update against them: an update that refers to anything else, or comes without a full log before it, marks the canvas unsupported until the next full log. If the agent can't fit an update into its batch, it gives it back to the hook, which sends it again with the next batch (as a full log if it was one). The viewer maps context object IDs to its own GL objects and replays calls in order; a full log for a canvas it already shows replaces that canvas with a new one, so replay starts from a fresh context rather than one carrying the previous log's objects and state.

Moli links programs without reflecting them and doesn't see GLSL ES 3 `in` attributes, so the hook answers program queries from the shaders' source: `getProgramParameter(ACTIVE_UNIFORMS / ACTIVE_ATTRIBUTES)`, `getActiveUniform`, `getActiveAttrib` and `getAttribLocation` come from a small preprocessor (`#define`, `#if`/`#ifdef`/`#elif`/`#else`, `defined()` and integer expressions) and the declarations it leaves, expanded as a browser reports them (`name[0]` for arrays, `lights[1].color` for structs). Attribute locations are those bound before linking, else the shader's `layout(location)`, else the first free ones. Declared but unused uniforms are reported active; the viewer's own compiler drops them, and calls on them (a null location, or an attribute at -1) are skipped there, as a browser would. Every standard WebGL1 and WebGL2 constant is filled in on the prototypes and constructors, and an extension the mirror can't replay is refused to the page (`getExtension` returns null) rather than marking the canvas unsupported. With these, three.js (r187, the image's, WebGL2) renders through the mirror, including a lit, textured `MeshStandardMaterial`. The source context’s alpha, depth, stencil, antialiasing and premultiplied-alpha attributes travel with the canvas; replay falls back visibly if the viewer cannot create a matching context. A sequence gap causes a fresh snapshot and full replay. Calls that cannot be mirrored mark that canvas unsupported rather than silently showing a stale or partial picture.

The supported command surface covers WebGL1 plus a broad WebGL2 rendering slice: shaders and programs, buffers, framebuffers and renderbuffers, vertex arrays, transform feedback, instanced and multi-target draws, integer and floating-point vertex inputs and uniforms, common fixed-function state, compressed and 2D/3D texture operations, and uploads from typed arrays or readable image, video, canvas and `ImageData` sources. Readable canvas sources are copied to bounded RGBA pixels at upload time; a source that is tainted or too large makes the canvas unsupported. Capability extensions include `OES_element_index_uint`, `OES_standard_derivatives`, `WEBGL_depth_texture`, float and half-float textures and color attachments, floating-point blending, `OES_draw_buffers_indexed` for per-attachment blending and color masks, anisotropic filtering, common S3TC, ETC, PVRTC, ATC, ASTC, BPTC and RGTC compressed texture formats, and WebGL1 method extensions `OES_vertex_array_object`, `ANGLE_instanced_arrays`, `WEBGL_draw_buffers`, and `WEBGL_multi_draw`; multi-draw batches are expanded into individual replay calls, so shaders using `gl_DrawID` are marked unsupported. Replay of compressed textures, floating-point color attachments, float blending and indexed per-attachment blending requires matching viewer extensions or equivalent WebGL2 core support. WebGL readback and query operations stay in Moli and may not match the viewer; less common extension methods and browser-specific extensions remain unsupported. Each context log is capped at 4,096 calls and 4 MiB; at a full color clear without scissor or color masking, prior draws for that framebuffer are compacted with repeated draw state, uniforms and replaceable streaming-buffer uploads into a replayable checkpoint. If depth or stencil writes have occurred, their buffers must be fully cleared too. Cross-frame state and buffer compaction runs only when no other target still has draw history that needs those values. Blits and multiple draw-buffer use disable compaction because their cross-target effects cannot be inferred safely; uncleared targets and persistent pixels retain their draw history and can reach the cap. Each texture upload is bounded to 2 MiB, WebGL payloads are capped at 3 MiB per change batch and 4 MiB per snapshot, and canvas dimensions are bounded. The server validates every operation and argument shape before forwarding it, including the extension precondition for WebGL1 aliases. The viewer validates again, checks shader and program compilation plus WebGL error state after each replay batch, replays retained commands after viewer-side context restoration, and falls back visibly if its WebGL implementation cannot replay a command. Shader and driver differences can still make a page's viewer rendering differ from Moli.

Implementation stages:

1. **Engine feasibility spike — partial (Moli 1.1.25).** Moli creates WebGL1 and WebGL2 contexts and exposes basic shader, buffer and draw methods, but its own raster output and readback were not reliable in the spike. The same screenshot path captured Canvas2D correctly. The viewer therefore replays supported WebGL1/WebGL2 commands in its own context; pages depending on WebGL readback or exact Moli state queries still need separate compatibility handling.
2. **WebGL command prototype — implemented.** `gogl.js` records a bounded allowlist in the page world, with compatibility shims for Moli's missing methods and state queries; the calls and extensions it records (`gogl-surface.js`, made from `gogl-surface.json`), its constants (`gogl-enums.js`) and its reading of shaders' source (`goglsl.js`) are files of their own, put in one function with it (`goGLPageJS`) so their names aren't the page's. Snapshots use a complete log, and updates use deltas.
3. **Ordered transport — implemented over `/go` changes.** A log travels as one object from the hook to the viewer, `{v: the calls (JSON), w, h, r: whole, version, attributes}` (`goGLLog`): in the hook's reply to the agent's capture (`gogl.js`'s capture protocol: `__tabtop_webgl_capture` takes it whole or since the last, `__tabtop_webgl_undo` gives it back when the agent's batch has no room), in a snapshot's canvas (`gl`) and in a change (`o: "g"`, `gl`). (A `/go` page open from before this shape, after the server's upgraded, shows WebGL canvases unavailable, and a page that keeps drawing is read again whole about once a second, each change it can't apply asking for it (`resync`, `goAgainEvery`), till it's reloaded: nothing reloads it by itself.) Dirty notifications avoid canvas readback polling; command delivery follows the existing sequenced changes and generation checks. Go validates operation names, argument shapes, array types, byte lengths and canvas dimensions before the viewer receives the stream (`gocanvasgl.go`), and checks each update's object references against what the canvas's earlier logs created. Updates follow the change polling (at most every 250 ms while the page changes), and a batch with a WebGL update is followed by another read at the least interval (100 ms).
4. **Viewer canvas and fallback — implemented.** A viewer-side WebGL canvas replays the log (`go-frame-gl.js`, loaded before `go-frame.js`, which makes it with the generation shown and a way to put a new canvas in one's place). A full log (a new snapshot after a sequence gap, a compacted log, a restored context) replays into a fresh canvas from the beginning. Unsupported operations and viewer replay failures show an accessible fallback label.
5. **Expand by measured compatibility.** Less common WebGL2 operations, additional method extensions, image sources that cannot be read, and detailed diagnostics remain future work. Keep unsupported operations visible, with a per-canvas fallback.
6. **Limits and rollout.** Command count, upload bytes, canvas dimensions, context history and JSON size are bounded. Source and viewer context restoration reset and replay the command history. Checked end to end (`test/go-check.mjs`, with Moli and headless Chrome): a WebGL1 and a WebGL2 scene, an animation started by a click routed to the engine and drawn past the 4,096-call cap (its log compacted and sent whole as it goes; several frames seen, then exactly its last, and a later click still reaching the page), a canvas drawn past the cap with no clear between (greyed out and labelled, its last frame not left), three.js turned by `requestAnimationFrame`, three.js's basic and standard materials, a canvas the page resizes and draws again, the viewer's context lost and given back (replayed from what it kept), WebGL in a same-origin and another site's embedded page, still and animating, a page with 20 WebGL canvases (16 mirrored, 4 labelled), and a shader the viewer can't compile shown as unavailable. `TestGoCanvasGL*` covers updates against the server's stream state, refusals and the three method lists (hook, server, viewer) agreeing; `test/gogl.test.mjs` covers the reflection, locations by name, and an update given back; `test/go-frame-gl.test.mjs` the viewer's bounds.

Embedded pages: a same-origin frame's canvases are read by the page's agent, by way of the page's own `gogl.js` (`__tabtop_frame_canvas` on the iframe), as Moli doesn't take the agent's events to a frame's page; the frame's hook says it's drawn on its iframe too. Its updates go as the page's do, with the iframe's number (`path`) for the copy to find the canvas in its frame's copy; one frame deep. (The hooks listen on the window, not the document: a frame navigated from its first, about:blank, document keeps its window, and Moli doesn't run them again.) Another site's frame (read in a world of its own, `goframes.go`) is mirrored whole each time the frame is read again: about once a second while it changes, less often if it keeps changing, so an animation there is slow.

Measured (headless Chrome with SwiftShader, Moli 1.1.25, the test site): a click to its new frame shown, 113 ms; the animation (200 calls a tick, every 150 ms, 31 colours) shown in every one of its frames, at about 66 KB/s; no main-thread task in the viewer over 50 ms while it plays; three.js's two scenes and 20 frames, 62 KB in all; the engine at most about 100 MiB and tabtopd 56 MiB through the check. (With reads at the poll's 250 ms alone, before a WebGL update brought the next read forward to 100 ms: 141 ms, 22 of the 31 frames, 27 KB/s.)

There is no switch of its own: WebGL replay is on wherever `/go` is (`WEB_GO`, itself off by default).

The viewer executes site-originated shaders and GL allocations in the user's browser. That adds GPU attack surface compared with the sanitized DOM renderer. Security review (2026-11-22), with what was changed for it:

- **No escape from the canvas found.** Replay calls only allowlisted methods, through the fixed extension-method tables; refs resolve only to objects the replay made; `JSON.parse` keeps `__proto__` an own property and typed-array names are checked with `Object.hasOwn`; nothing reaches the DOM but constant labels; nothing about replay (results, errors, timings) goes back to the page, the server or the engine, so the page can't read the user's GPU or pixels.
- **Allocations, draws and contexts are bounded in the viewer** (`glCheck`): textures and renderbuffers at most 4096 × 4096 (and 256 deep, 64 M texels, 13 levels, 8 samples), buffers and pixel-buffer uploads 64 MiB, draws 16 M vertices (instances 1 M), and each context's storage 256 MiB as bound at the time (storage given again replaces, deletion gives back). At most 16 mirrored canvases at once; a document's 17th and later are labelled unsupported by the server too (`goGLStreamsMax`). A failed or dropped mirror loses its context (`WEBGL_lose_context`), freeing GPU memory.
- **GPU resets:** a lost viewer context is given back and replayed at most once, never for one whose replay failed; contexts lost within a second of each other are one reset, and three resets in a minute turn WebGL replay off in that viewer for new canvases for a minute, each time again after for twice as long as the last (up to about 17 hours), so a log that resets the GPU isn't replayed again and again, nor a page that keeps making new canvases let go on; one reset losing several canvases, or a few over a long session, doesn't turn it off. (A canvas left unavailable meanwhile stays so till its page is loaded again.)
- **Server:** only the extensions the viewer replays are accepted (names were unbounded in its per-canvas state); a command's keys must be exactly the known ones, as `encoding/json` matches keys without regard to case and the viewer would otherwise replay what wasn't checked (`{"a":…,"A":…}`).
- **Tables in one file:** the calls, WebGL2's calls, the extensions (in the order the page is told them) and their calls, the calls taking strings and a log's limits are `gogl-surface.json`. The server embeds it (`gocanvasgl.go`); `go generate` makes `gogl-surface.js` of it, which `goGLPageJS` puts inside the hook's function (so the page can't see it) and `go-frame.html` loads before `go-frame-gl.js`. `TestGoGLSurfaceGenerated` fails if the script is older than the JSON, and `TestGoGLSurfaceInStep` checks the tables against each other. The hook's and the viewer's other lists (the queries answered in the engine, what replay needs of the GPU) are their own.
- **Types:** where WebGL wants a number, a string or an array would be turned into one past the bounds; both the server and the viewer allow strings and arrays only to the calls that take them. Storage is counted to what `bindBufferBase`/`bindBufferRange` and each vertex array's element buffer bind; storage given with nothing bound is refused. GL's error is asked after each allocation, so a binding GL refused (which the budget would have taken as made) ends the replay before storage can be counted to the wrong object; deleting the bound vertex array, and binding a transform feedback object, are followed too.
- **Frames:** the agent hands nothing of its world to a frame's document (whose methods the page may replace); a same-origin frame's canvases are read only through the page's `gogl.js` relay, and the viewer follows an update's `path` only through frames the page's agent read.
- **First read:** a context's first read is always a full log (a canvas given a context after the page was read would otherwise have its calls refused as an update with no log before it).
- **Accepted:** shader cost (a long-running shader) is bounded only by the browser's GPU watchdog and the reset policy above; a page can tell it's mirrored (the capture events are visible to it); a remote page gets real GPU and driver surface in the user's browser, which is why it's on only where `/go` is, and why a per-site or global switch is a reasonable product decision.

### Sharing, location, picture-in-picture, and PNG paste

On supporting viewers, a top-level HTTPS page can share text and HTTP(S) links (and files, below) through the native share sheet or request the viewer’s location once with `getCurrentPosition()`. The viewer names the requesting origin and asks on each request. Sharing and entering picture-in-picture require recent input in the remote page. The native action runs from a button in the viewer so it receives a fresh user gesture. A video with an existing viewer player can enter and leave picture-in-picture through the page’s API. Resizing or closing the floating window updates the page.

A page can follow the location too (`watchPosition`, `clearWatch`; godevice.js, `godevice.go`, go-device.js): asked as once is ("wants to follow your location (until you stop it, or leave the page)"), the viewer's own `watchPosition` runs, its first position the answer, those after sent as they come (the newest each 250 ms at most, none lost: the last is where the person is), its errors too, each passed to the page's watchers (one watch in the viewer for all of them, high accuracy if any asks it). While it's followed the viewer says so (a bar at the foot: "*origin* is following your location", **Stop**). It ends when the page clears its last watcher (`location-stop`), when the person presses Stop (the page's watchers given a permission error), when the viewer's browser refuses it, or when the page is left. The server passes on only the watch it allowed, of the page shown, each 100 ms at most, each position checked as once is. Checked end to end (go-check, headless Chrome's position overridden): once; followed, a moved position passed on, the bar shown; cleared by the page and by Stop, nothing after. Unit: `TestGoLocationWatch`, go-device.test.mjs.

**Files shared** (`navigator.share({ files })`, godevice.js, `godevice.go`, go-device.js): where the person's browser shares files (`canShare({files})`, told as a tab connects: `shareFiles`), the page's Files (10, 100 MB in all, at most) go to it as file streams of their own (gomedia.js's `relayFile`, asked in the page's world, marked shared), and the request names them by number. A trusted paste in the rendered document forwards one PNG, up to 8 MiB, to the original element, including in a mirrored frame. **File System Access pickers** (`showOpenFilePicker()` and `showSaveFilePicker()`, godevice.js, godevice.go, go-device.js, gofs.go): on a supporting viewer and an HTTPS page, the page can ask for files to open or a destination to save to. The viewer identifies the requesting origin, then its own Allow button opens the browser's native picker with the page's file type filters. Opened files stream through the tunnel in acknowledged binary chunks into private temporary files in the engine's run directory. The engine attaches each staged path as a native, disk-backed `File` (`DOM.setFileInputFiles` on a hidden input the agent makes; the page's world is told the input's id and takes the `File` from it, as an object in an event's detail doesn't pass from the agent's world to the page's), so `getFile()` does not assemble the entire file in page memory. A file read again is staged once; a save destination's handle reads too, its staged copy let go as a write to it closes. Writes to the selected save destination cross the tunnel in 24 KiB chunks; a writable stream supports `write`, `seek`, `truncate`, `close`, and `abort`, including writes through `getWriter()`. The pieces are pipelined: the page keeps up to 32 in flight, each answered by its own id; the agent takes 16 a read (apart from the other asks' 4, cancelling those it takes so the page keeps the rest), the server sends them on without the one-ask slot (64 waiting at most) and reads again in 100 ms while they flow, and the person's browser writes them in turn. Measured in go-check: 2 MB saved and read back in 1.3 s (one piece a round trip, 100 KB took 2.6 s). Only a save destination's handle is written: an opened file's is read only, as the person chose it (refused by the page's shim, the server and the person's browser alike; its `queryPermission({mode: "readwrite"})` says `prompt`, and `requestPermission` doesn't raise it). Handles and staged files are cleared when the page changes or the viewer session ends; directory pickers and persistent handles aren't implemented. A read is capped at 512 MiB per file and 1 GiB staged per page, using `/go`'s existing file upload quotas; opening more than 32 handles at once is refused. The API is exposed only when the viewer browser supports both native pickers.

### Performance

Measured on the same machine, Wikipedia, GitHub, Hacker News and www.sg, before and after (November 2026):

- **The snapshot is read at DOMContentLoaded**, not the load event: 0.05–0.4 s sooner (Wikipedia’s document is ready at 0.37 s, loaded at 0.70 s).
- **Changes that come while the frame builds a page are kept** and applied once it’s shown, in order. They were dropped, so the next batch named nodes the copy never had, and the whole page was read and sent again (Wikipedia: a second 736 KB snapshot and rebuild). Re-reads after this: none in the measured run.
- **Large messages are compressed** (`sendLarge`): snapshots, change batches and frames from 16 KiB, raw deflate at its fastest, if they shrink by a tenth, as binary messages of request number 0 (resources’ bytes start with theirs); the page says it can decompress (`DecompressionStream`) when it opens the tunnel, and takes messages in order, a compressed one before what follows it. Wikipedia’s snapshot is 124 KB instead of 630 KB, GitHub’s 91 KB instead of 620 KB: on a distant connection, about half a second less a large page.
- **The frame keeps a tab’s resources and stylesheets**: blob URLs across pages (1,500 or 256 MiB, the oldest revoked), and each stylesheet as rewritten, by address (32 MiB), dropped with any blob it may use. A site’s pages no longer parse and rewrite its stylesheets each time: GitHub’s 7.6 MB of CSS, about 0.8 s, once a tab (its page built in 0.5 s on a second visit, from 0.9 s).
- **A new page is shown settled** (November 2026, YouTube): the page before stays in view (inert: what’s done to it is for a page the engine has left) while the new one is built out of view, its stylesheets waited for (12 s at most, from 5: on a slow link a page was shown unstyled, then restyled), then until it settles: no change for 300 ms while the engine has at most two requests going (`go-net`, from the engine’s `Network` events; a long poll or a beacon mustn’t hold it), 4 s at most. YouTube had been drawn three times, unstyled, then as its grey skeleton, then built; its skeleton came 8.5 s in and its content 3–5 s later, so it’s now shown once, built, or as the skeleton at the cap.
- **Batches for the page shown are drawn once a frame** (`requestAnimationFrame`), all of those that came in it, and what a batch adds is hidden until the stylesheets it brought have come (2 s at most), so content a script adds isn’t seen unstyled.
- Left as they are: the engine’s own loading (mostly the sites and the network), and the agent’s read (0.25 s of its own on Wikipedia, mostly Moli’s attribute access; more while the page’s scripts are still busy).

### What the page fetches (`data:` URLs)

- `gofetch.js` patches the page’s `fetch` for `data:` URLs (in the same `Page.addScriptToEvaluateOnNewDocument`, before any of its scripts). Engines fetch `data:` URLs themselves (XHR always has), but a page’s CSP forbidding them — `connect-src` without `data:`, typical of sites that never fetch `data:` — refuses the fetch before the engine’s is asked, and pages that do fetch `data:` (inline datasets, self-contained exports) break.
- Those fetches are answered in the page instead: the URL’s own bytes, decoded the way `data:` URLs are (the fetch standard’s data: URL processor), in a `Response`. No request is made, so there’s nothing for the page’s CSP or the engine’s proxy to refuse; every other URL goes to the engine’s fetch as before, and a `data:` fetch sends nothing anywhere, so the engine’s address policy is untouched.
- Workers aren’t covered: their globals are the engine’s to start, not the page’s documents, and a `data:` fetch there goes as it would in a browser.
- Measured with Moli 1.1.25: under the page’s `connect-src 'none'` it refuses a `data:` fetch (“blocked by Content Security Policy for `data`”); with the patch, base64 and percent-encoded `data:` URLs are answered, and a fetch of any other address still goes to the engine’s own `fetch`, which the page’s CSP still refuses (`TestGoFetchDataWithMoli`). XHR isn’t patched.

### Events

- The mouse and keys are given to the engine as a browser’s own input (`goinput.go`: `Input.dispatchMouseEvent`, `Input.dispatchKeyEvent`), so the page gets trusted events and the engine does what a browser does with them: a click from a press and release, a double click, a context menu, focus, Enter sending a form, Space pressing a button, Tab moving on; hover menus, buttons that listen only for the pointer, and the wheel work.
- A pointer event names the element under the pointer and where within it, as fractions across and down, since the copy is laid out by the person’s browser. The engine scrolls it into view if it must (`block: "nearest"`), lays out again with a one-pixel screenshot (`relayout`) (neither a scroll nor a change of class does), finds that place in it, or its middle if something else is there, and gives the input there. If neither is on it (the engine has something over it the copy left out, an iframe say), a press is done as before, by script, as a click on release. A press is given or scripted once, at the press; its release follows it; a press let go outside the frame, or the window left, is let go away from the page (not a click).
- What’s typed is typed in the copy and sent as the field’s value; keys go as `rawKeyDown`, which do what keys do but type nothing, except Enter in a one-line field, given with its text, which sends the form. The engine gives the key’s element the focus first, unless it’s the document itself. Clicks the copy makes from a key the engine was given (Enter, Space) aren’t sent again.
- **Rich text** (`contenteditable`: `true`, empty, or `plaintext-only`; `false` or a value that's none of these as HTML has it, a missing one inherited) has no value to send: it's edited in the engine, as typed, and its result (and caret) comes back.
  - **Keys:** one that edits (a character, Enter, Backspace, Delete; Ctrl/⌘ with B, I, U, Z, Y) isn't done in the copy, but goes as typed (`keyDown` with its text), so the page has its `keydown`, then its `beforeinput`, as in a browser: a chat box's Enter sends. The copy's selection goes with it once the person's moved it there (a click, a tap; an arrow, Home, End, Page Up or Down, Ctrl+A; not Shift, nor a phone keyboard's key): otherwise the engine's is where its last edit left it (each key sent with the copy's caret, which only moves as the engine's comes back, would have fast typing go in at one place, last first).
  - **Edits that aren't keys** (a phone's keyboard, an IME's word, once it's chosen; a spelling fixed, a range the browser names; a cut; a paste, its text and HTML): sent as an edit (`edit`: its `inputType`), given as the key that makes it, or text put in (`Input.insertText`). A paste is offered to the page as one (a `paste` event with both); not taken, it's put in styled in rich text (its markup only what styles or orders it, none of its attributes but a link's web address) or as its text in `plaintext-only` (lines broken as Shift+Enter breaks them).
  - **What Moli doesn't do** of an edit the page lets be (measured: Backspace and Delete fire `beforeinput` and delete nothing; Enter puts a `\n` in the text; Ctrl+Backspace is said as a character's deletion) the agent does, as a browser would (`editDefault`): characters, words and selections deleted, paragraphs joined at their edges, a new paragraph (a line, in `plaintext-only`), a line break; the page told by `input`. A page that takes the edit (cancels `beforeinput`) has it left to it.
  - **Back:** a batch that changes the rich text focused carries the engine's caret (`sel`), and the copy's put there. An embedded page's rich text is edited by script there (its `beforeinput`, then the edit), in its own document (Moli's selection there has a range it won't give: made from its ends); its caret isn't sent back. Tab goes to an editing host, not rich text within another's, nor one that's `false`.
  - **Limits:** a click or arrow made before the engine's caret has come back sends the copy's caret as it is, which may not have the edits still coming in. Ctrl+Z and Ctrl+B, I, U go to the page as keys, and do what it does with them (Moli does nothing of its own). An engine that refuses key input drops the edit (the scripted fallback is for embedded pages).
  - Checked end to end (go-check): typed, deleted, a new paragraph, Shift between keys, text and an IME's word put in (one begun as a change comes back, one in a box that's empty), typed where the caret was moved, paragraphs joined, a chat box's Enter, an embedded page's (its focus kept as it's redrawn), and an editor as frameworks make them (each edit taken, its box made anew from its model, its caret kept by `selectionchange`, which Moli fires for the agent's selection); and in Moli (`TestGoRichTextWithMoli`) each edit the agent does, `plaintext-only`'s Enter, a paste styled, given back, or taken, and the page's own edits left alone. Not checked: a paste from the person's clipboard end to end (headless Chrome's), drag and drop of text into rich text.
- Moves and the wheel go at most every 50 ms, the newest kept (the wheel’s turns added up), one at a time on the acts’ queue, dropped while a dialog’s open; presses and keys are never dropped for them. A press or key that opens a dialog waits for it (up to the dialog’s minute), and is never given twice.
- Where the person scrolls an element (or the page) to is given to the engine, the newest place every 100 ms, while scrolling follows their input (3 s of it): a swipe, a fling, a scrollbar or a key scrolls the copy, not the engine, and a page that goes by where it’s scrolled (a feed playing the video scrolled to) needs to see it. The agent scrolls the element there (`behavior: "instant"`) and, as Moli fires scroll events only as it renders (which it doesn’t), fires `scroll` itself if it moved.
- Touches are given as touch input (`Input.dispatchTouchEvent`), each finger as the element under it and where within it, as the mouse’s; their moves as the mouse’s, the newest every 50 ms. The engine makes a tap’s click itself and a swipe’s none (Moli, measured: a long swipe doesn’t click), so the mouse events the person’s browser makes from a touch aren’t sent as well; a tap the engine can’t be given is a scripted click, as a press is. Swipes still scroll the copy, given to the engine as scrolling (above); a page’s own swipe handling (a carousel) sees the touches.
- Drag and drop within the page is the engine’s: Moli drags from the mouse it’s given as a browser does (`dragstart` to `drop`, with the page’s data). The person’s browser doesn’t start its own drag of the copy (it would keep the mouse’s moves and release). What’s dragged in from outside (text, a link, HTML, at most 32 KiB) is given with `Input.dispatchDragEvent`: its kinds as it’s dragged over, itself when dropped, at the element and place under it; files aren’t (the remote browser takes no files: the person is told).
- Sites get pointer movement and key timing, as in a browser. Not covered: files dropped or chosen, typing by IME into the engine (the copy’s value is sent), and typing in `contenteditable` (the copy’s edits aren’t sent).
- Otherwise (and when the engine won’t take input) the agent does it in the engine (`__tabtop.act`): `click()`, the value set through the element’s own setter followed by `input` and `change` events, keys as `keydown`/`keypress`/`keyup` (Enter in a field sends its form, as browsers do), `requestSubmit()`. Acts run in order on their own queue, so a page’s dialog can’t hold up reads. Coordinate-based input (`Input.dispatchMouseEvent`) is not used: the shown copy is laid out by the person’s browser, not the engine, so places on it aren’t the engine’s. An SVG element (a button’s icon) has no `click()`, so it’s sent a click event, which reaches its button.
- `alert`, `confirm` and `prompt` stop the whole engine until answered (`Page.handleJavaScriptDialog`); they’re asked in the trusted UI, a modal dialog over the page (a prompt with its default, Cancel answering `null`), whether the page asks as it loads, from a frame or from an act. They’re answered by the engine’s dialog events, not by replacing the page’s functions: those answer synchronously, which only the engine stopped can wait for. One unanswered for a minute is answered (OK to an alert, no to a question); `beforeunload` is always let go. From a page’s second, the dialog offers “Don’t let this page ask again”: ticked, its later dialogs are answered by the server the same way, unasked, so a page asking in a loop (or on every key) can’t keep the person answering (as browsers stop a page’s dialogs); a new page may ask again. `window.open` and `target=_blank` load in the same tab (the new target is closed).
- A document Moli loads as text that isn’t one (a PDF, an archive) is recognised by the type in `Network.responseReceived` (Moli’s `document.contentType` says `text/html`, and its MIME types keep their parameters) and offered to save into Downloads.
- The engine performs any default action itself; resulting navigations and DOM changes come back as messages.
- Input values are sent with `input` and `change` events, so the engine’s form state matches what the user sees.
- Navigations always go through the trusted UI’s history and address bar, never through the frame.
- Downloads are reported to the trusted UI, which can hand them to the existing fetch-to-Downloads flow in `fetch.go` with user confirmation, naming the file’s host. That fetch (`from_go`) uses a client that may reach private networks only when both `WEB_GO_FETCH_PRIVATE` and `WEB_GO_PRIVATE` allow it: the site chose the address and may redirect the second request elsewhere.
- A dialog is attributed to the document that opened it (the dialog event’s URL, or the main frame’s last committed address), not to the address bar, which a popup loading in the tab may already have changed.
- The frame’s token is handed out once per frame document. A whole-document re-read (on a gap in changes, or a batch too large) happens at most once a second per tab, and at most 64 of the person’s acts wait for a page that isn’t taking them; more are dropped.
- The page’s address isn’t in the tab’s own (`/go/`, never `/go/#<address>`), so the browser’s history (and its sync) and anyone seeing the screen don’t get it: a reload carries on from `sessionStorage`, this tab’s alone. It never was in a request (a fragment isn’t sent; clicked links and typed addresses go inside the tunnel). A link to `/go/#<address>` from elsewhere still works: the address is taken out of the tab’s address at once, and waits in the toolbar for Enter.
- The tab's own history has an entry for each page shown here, on `/go/` itself and holding only which page it is (`{goAt: n}`), so a phone's back (a swipe, a button) goes back a page here rather than leaving; the bar's back and forward go by it too, so they stay in step. Its pages back and forward are kept in `sessionStorage` (the last 50) for a reload.
- The bar (`go.html`) is one row: back, forward (in the menu on a phone, for room), the address, and a menu at its end holding forward and the other pages' links and logging out (the bar of links the other pages have at the top; the session's warning, which goes in that bar, is shown below this one, the login summary at the bottom). The address shows the site only (the words, for a search; `http://` before a site that isn't https) until it's edited, the whole address then (and in `data-url`); reload, or stop while loading, sits at its end, clear while it's edited. Words that aren't an address are searched with the engine chosen in Settings (`searchEngine` in the site settings; DuckDuckGo HTML by default), and so is what starts `http://` or `https://` but isn't an address at all (no host that's one: `https://exa mple.com`, which Chrome's own `URL` takes as `exa%20mple.com`), as typed; one with a name and password is an address, refused by the server as before. A page slow to come (a second) has the one being left dimmed and its players paused. The start says what /go does, and lists the sites opened lately (their origins only, in this device's `localStorage`, never sent anywhere; one button forgets them).
- The engine's window is the copy's layout size, not the frame's: the copy's scroll bars left out (the copy says its root's `clientWidth` and `clientHeight` as they change, `{type: "layout"}`). The engine has none, so it laid a page out 15 pixels wider than the copy shows it (a classic scroll bar), and what a page places by its width was off: mi.com/sg's hero carousel showed half of one slide and the edge of the next, at a phone's width and on a desktop. The copy's root is replaced by each page's, so what observes it (this, the players' places) is moved to each new one; before, it watched the first page's alone.
- On a phone: the page is `viewport-fit=cover`, and the bar is kept below a notch (`env(safe-area-inset-top)`), the bar and the page clear of rounded corners and the home bar (left, right, bottom insets), as are the status and the login summary; checked with Chrome's emulated insets. Pull-to-refresh and overscroll bounce are off (`overscroll-behavior: none`): a pull at the top would have reloaded /go itself, not the page shown.
- A device's keyboard, up for typing in the address or the page, makes the frame shorter but not the engine's window: the page isn't laid out again, nor its scripts told of a resize, each time (a phone's browser keeps a page's layout as its keyboard comes and goes); the copy keeps the field being typed in in view.
- Unsupported features (WebRTC, media streamed by a site’s own player, popups, and Canvas2D or WebGL canvases that cannot be mirrored) are rendered as placeholders and reported through diagnostics. Readable Canvas2D canvases are copied as bounded PNG snapshots; WebGL uses bounded command replay (section 6).

## 8. Verification

Use local fixture sites and browser automation to verify:

- DOM rendering, mutations, events (including `preventDefault` on links and forms), form input, redirects, and resource resolution.
- No destination traffic leaves the client directly, including with the sanitizer and rewriter disabled (CSP alone must block it).
- Sanitizer bypasses through HTML, CSS, SVG, and mutation batches.
- Attempts from snapshot content to access the parent DOM, session storage, tunnel credentials, or files.
- From inside the engine sandbox: reading `$HOME`, roots, or TabTop state; reaching tabtopd sockets other than CDP; connecting to private, loopback, metadata, or host addresses directly, via the proxy, or via redirects and DNS rebinding. Include page requests to every spelling of localhost and WebSocket connections, and repeat the network checks in unsandboxed mode, where the proxy is the only barrier.
- Resource exhaustion: infinite loops (Moli’s watchdog, then tabtopd’s), memory growth (the cgroup limit or tabtopd’s watchdog kills it), process forks, oversized and compressed responses.
- Stale navigation generations are dropped by the server.
- Logout, session expiry, and tunnel loss kill the engine and delete its scratch directory.
- Exact sandbox and CSP values for the `/go` frame.
- No unexpected hosts: every destination in the egress proxy log belongs to the pages loaded.
